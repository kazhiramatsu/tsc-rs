# H2.7e m-2: ordinary non-bundle declaration-map execution

This packet connects the m-1 recorder to ordinary whole-Program emit with
`declaration: true`. It admits the non-bundle declaration-map member in the
existing output plan and uses the existing sink, diagnostic and CLI paths.
The active global profile and H2.7e activity/adoption markers are unchanged;
this is a semantic implementation packet, not H2.7e corpus closure.

## Execution and boundaries

The declaration unit constructs recording inputs after the existing
`declBlocked` gate, prints through the declaration handler, and returns the
map, declaration and source-map observation. The executor retains callback
order: JavaScript map, JavaScript, declaration map, declaration, omitting
members absent from the selected mode. It lists each text before its map.
Declaration-map list membership follows the actual print branch and does not
depend on the map sink's `SkippedUnchanged` disposition. A skipped declaration
write removes only the declaration's list entry. Write failures continue
through the existing TS5033 producer and remain in the emitted-file list.

The source-map result list is allocated for `sourceMap`, `inlineSourceMap`,
or effective declaration maps. JavaScript recording uses only the first two
flags. This separation prevents `declarationMap` from creating an unrequested
JavaScript map. The implementation follows TypeScript 6.0.3 `emitFiles`
(`_tsc.js:116530-116858`) and the m-1 authority notes. It does not adopt the
pinned native emitter's different failure/list ordering documented in the
API observation packet.

Getter and forced declaration-map operations retain typed `declarationMap`
refusal. Ordinary `declarationMap: true` with declarations disabled or
unspecified retains the same refusal, including its zero-activity contract.
That option intersection's TS5069/JavaScript-only behavior belongs to the
subsequent API packet. In particular, no forced disabled-declaration Debug
Failure is converted into a Rust success. Bundle `outFile`, targeted ordinary
emit, and other existing option refusals remain in their respective owners.

## Complete observations and comparison facets

The original `declaration-maps.json` remains byte-for-byte unchanged: its 24
controls all use the ordinary command with `emitDeclarationOnly: true`.
The dedicated test now runs each twice through `load_emitting_program` and
`ProgramSession::emit_with_reported_diagnostics_for_harness`, with original
options and absolute virtual paths and pinned libraries mounted at `/lib`.
It compares reported and emit diagnostics (including related information),
emitSkipped/refusal alias, emittedFiles presence/order, sourceMaps
presence/order and full map payloads, every callback's position/path/kind,
source association, metadata, BOM and callback/materialized bytes.

The same observer has a `--runtime` mode that creates a separate three-case
`declaration-maps-runtime.json`. Each uses two files and ordinary JavaScript
plus declaration output: declaration maps alone, both external maps, and
inline JavaScript maps with external declaration maps. These observations
repeat twice and compare through the same Program path. They expose the
independent recording flags and interleaved source-map/callback/list order.

All 27 controls additionally execute the real `tsc-rs` binary. A temporary
project relocates the `/project` inputs and absolute declarationDir before
execution; enum options become their equivalent config spellings. The CLI's
actual TSFILE status lines and process exit code must equal the corresponding
frozen command facets under that explicit input relocation. Every fixture is
covered, including TS5051 sourceRoot controls, BOM/newline options and both
map lanes. Config diagnostic locations are not substituted for the original
Program command tuples: those are compared with their original virtual paths
by the Program test. No helper assumes that status output is empty.

Seven cases from `declaration-map-apis.json` cover ordinary map/declaration
onError, both onError, map/declaration skipped writes, and map/declaration
System failure. Each runs twice through the actual Program and OutputSink
boundary. System cases wrap the existing `FsOutputSink` around a controlled
`EmitFileSystem`, checking both write attempts, exact bytes and successful
materialization indices. API cases compare the full result/diagnostic/map
and callback observations, including callback data before and after feedback.
The immutable Rust text metadata represents data before the callback;
`SkippedUnchanged` carries the upstream `skippedDtsWrite` feedback. Map
callbacks have no such metadata, which the final listing preserves.

Four additional ordinary calls from that same API fixture cover
noEmitOnError's absent sourceMaps, isolated-declaration blocking with maps
retained for only the successful source, and the present empty sourceMaps
of empty and declaration-only Programs. The surrounding getter operations
remain refused; these comparisons exercise the recorded ordinary command
result on a fresh Program, without admitting those getter APIs.

The five failure controls additionally execute the real CLI with directories
occupying the failed output filenames. Their actual TSFILE status lines and
exit code match the frozen controls; the original controlled TS5033 diagnostic
text is compared by the Program sink test. The skip controls use the same
emitted-file/result producer. No real CLI skip claim is made:
`FsOutputSink` does not return `SkippedUnchanged`. Direct JavaScript callback
throws and their partial writes remain frozen observations outside the Rust
`Result`-based sink protocol; they are not compared as TS5033 successes. The
packet does not claim getter/forced, builder or bundle runtime admission from
these references.
