## r27 review: missing-await admission predicate

**Predicate soundness (recovery.rs `is_literal_or_missing_await`).** No over-admission found. It short-circuits on `is_literal_only`, so every clean or literal-only input keeps today's verdict; a module with a `Reparsed` action still enters through that branch, as required. The structural branch refuses: silent missing nodes (`missing_node` None), deduped attempts (`diagnostic_index` None), non-Identifier missing kinds, duplicate full-starts, any action, and any reachable zero-width Identifier whose parent is not `AwaitExpression` or that has no record. `missing_positions.is_empty()` refusing pure report-only sets matches the stated scope. The three-attempt asyncFunctionDeclaration10 shape is refused twice over (two `missing_node: None` structural events and a `ListAbort` skip).

**Provenance the predicate does not check, and should not need to.** It does not verify the diagnostic code or that the `AwaitExpression` carries the error flag. Both are implied by the producer (`create_identifier_node` → `create_missing_node` with `Expression_expected`) and the reachable-walk match; adding a code check would turn a structural predicate into a code allowlist, which you excluded.

**One conservative blind spot to record, not fix.** Any module file whose first pass triggers `reparseTopLevelAwait` carries a `Reparsed` action, so a missing await operand inside an ordinary async function in such a file is refused even though the missing node is unrelated to the run. tsc emits it (`await ;` at top level also emits). Keep refusing for now; the census should count that population separately (`Reparsed` present, otherwise admissible) so it is not mistaken for a predicate bug later.

**Emitter/printer reachability for a zero-width operand.** es2017 `visit_await_expression` forwards the operand into the yield (es2017.rs:722-743); es2018 `visit_async_generator_await` visits it with `visit_required` (es2018.rs:1856-1859) and wraps it in `__await(<empty>)`; the generators pass carries the yield operand into `[4 /*yield*/, <empty>]`. Nothing special-cases empty text, which is what upstream does. Native probes (vendored tsc) give the byte contracts to compare, and two are non-obvious:

- `async function f(a = await /*c*/) {}`: ESNext prints `await  /*c*/` (two spaces, the comment is the missing node's trailing comment); ES2015 prints `function* (a = yield  /*c*/)`; ES5 moves the comment onto the parameter, `function (a /*c*/)`, with `a = _a.sent()` inside. This is the highest-value control because it exercises trailing-comment ownership of a zero-width range plus the default-parameter lowering.
- `async function* g() { await ; yield await ; }`: ES2015 prints `yield __await();` and `yield yield __await(yield __await());`, an empty call-argument list from a zero-width argument.

Other confirmed-admissible shapes worth adding as positive controls: `await;` in a body, `return await await ;` (one missing node, parent AwaitExpression), `{ [await ]: 1 }` at ES5 (computed-key lowering with `_a = {}`), and `async () => { await` at EOF (report-at-current-position path, diagnostic length 0). Negative controls that the predicate must refuse: `await ();` (missing node parent is `ParenthesizedExpression`), `function f() { return await ; }` (no diagnostic, `await` is an identifier, already admitted today), and `export {}; await ;` (Reparsed).

**Source maps.** For each admitted row compare `.js.map`, not only bytes: upstream emits one mapping at the shared pos/end of the zero-width node, deduplicated by the generator. The Rust recorder accepts `start == end` (position.rs:14), so any divergence here is a printer boundary issue, not a parser one.

**Census gaps.** `program_facts` uses the acceptance loaders, so parse options project correctly for corpus rows. It does not cover the fixture families under `crates/compiler/tests/fixtures` (the ordinary 551 and CLI inputs), which is where the r17 comment controls live; add those inputs as a third census source or state explicitly that the census is corpus-only. `Verdict::of` in the new mode correctly uses `literal_only` as "before", and legacy mode is unchanged.
