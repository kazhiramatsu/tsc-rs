## r38: corrected provenance and what I could and could not pin

**Upstream producer, verified.** `cloneNode` does not copy positions; my r37 claim was wrong. The `after` dump shows the module transform leaves `BinaryExpression[-1,-1]` (original = `BindingElement[12,52]`) whose **left operand is the parsed `Identifier[12,52]` itself** (`getParseTreeNode(left) === left`). `collectExportedVariableInfo` registers `exportedBindings` only when `isLocalName(decl.name)` holds, so `getExports(name)` is undefined for a binding-element name and `createAllExportExpressions` returns a plain `createAssignment(name, value)`. The `exports.someMethod` spelling is produced at print time by the module transform's `substituteExpressionIdentifier` (_tsc.js:111955-111965): `getReferencedExportContainer(node)` is the SourceFile, so it returns `setTextRange(createPropertyAccessExpression(exports, cloneNode(node)), node)`. The comment phase runs on that substitute, whose range is the identifier's full range starting after `{`, and the own-line JSDoc is its leading trivia. Same-line comments are not collected (tsc's `iterateCommentRanges` only starts collecting after a line break), which is why the renamed leaf `{ /** c */ a: b }` prints nothing: its range starts at `b`.

**Rust producer, verified.** Rust diverges structurally but not in bytes: `CommonJsModuleInfo` registers binding-pattern leaves in `exported_bindings` and `direct_exported_variable_names` (builtins.rs 3915-3940), so `export_assignment_plan` returns `direct_export_storage = true` for `someMethod` and `create_module_export_assignment` builds the access at transform time: `create_export_access_from_module_name` (clone with synthesized positions) then `set_text_range(access, target)` with the parsed name (raw 392/437, per your probe). The leaf then gets `set_original_node(assignment, BindingElement)`; the single expression is not wrapped; the statement gets `set_original_and_range(statement, VariableStatement)` and no `NO_COMMENTS` (that flag is only set in the arrow/function/class initializer branch, matching tsc's `removeCommentsOnExpressions`).

**Printer gates I traced and ruled out.** `comment_range_for_node` falls back to raw positions; `emit_leading_comments_for_comment_phase_owner` suppresses only on `comments_disabled`, `NO_LEADING_COMMENTS`, a rangeless owner, or `NotEmittedStatement`; the resume-past-parent rule fires only when the container position equals the owner start, and the enclosing statement's container position is the `VariableStatement` full start, not 392; `collect_source_comment_ranges` ports the after-newline collection rule (source has LF only, 0 CR); the single `NO_NESTED_COMMENTS` producer is the import-equals path and the sticky `comments_disabled_after_failure` is reset on success; the BinaryExpression arm hands the left operand to `emit_expression_child_with_source_comments` with a nested `LeadingAndTrailing` deferral, so the access's own leading phase is reached unless the state is `Pending` or the context carries nested suppression. Neither the factory's property-access constructor nor `create_assignment` stamps comment flags.

**Re-export implication (independent of the gate).** Rust also `set_text_range(expression, original)` on wrapper export assignments (the multi-export loop), while tsc's wrappers are rangeless and only the substituted identifier carries the range. Keep only `set_original_node` on wrappers and re-check maps in that control.
