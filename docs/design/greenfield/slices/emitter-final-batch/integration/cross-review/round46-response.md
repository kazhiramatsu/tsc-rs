Both mechanisms are traced; writing up the minimal fixes with upstream locations now.

**A. ES5 CJS/AMD/UMD comment-map rows (24): the statement's source-map range, not the access.**

Decoded maps: native emits gen 3:0 ← src 3:1 (`x`) and then gen 3:0 ← src 2:1 (the comment); TS emits only gen 3:0 ← src 2:1. tsc's `addMapping` (_tsc.js:92450-92476, ported faithfully in the Rust generator) keeps one pending mapping per generated position and simply overwrites its source when a later, non-backtracking source arrives; a backtracking source commits the pending one and starts another. So the two-segment output means the statement recorded a map at `x` (line 3) *before* the comment (line 2) was written, and the comment backtracked. Upstream's statement is ranged to the whole VariableStatement (`setTextRange(createExpressionStatement(...), node)`, 111597): its start map points at `export` on line 1, and the comment on line 2 overwrites it at the same generated position, leaving one segment. Rust does the same `set_original_and_range(statement, original)` but then calls `set_direct_export_statement_range(statement, name, original)` (builtins.rs:6820, helper ~11160), which replaces the statement's source-map range with `[name.pos, statement.end)`. The name range starts after the comment, so the comment backtracks and both segments survive.

Fix: delete the `set_direct_export_statement_range` call and helper; the statement keeps the VariableStatement range, exactly upstream line 61. The no-comment rows are unaffected, because the access's own start map (at `x`) overwrites the statement's `export` map at the same generated column either way. This is also why the ES2015+ pattern path, which already records `exported_range_name = None`, passes. One thing to confirm on replay: AMD/UMD rows are indented inside the factory, so the statement map and the access map must be recorded at the same column (tsc's `getColumn` reports pending indentation); the passing AMD/UMD no-comment rows indicate the Rust writer already does this. Upstream: the flattened ES5 statement is the same VariableStatement node (`updateVariableStatement`), so no other range is involved.

**B. System `default-re-export` (4 rows): two independent defects in the System flatten, both in system.rs.**

1. Hoist order `var x, _a` vs `var _a, x`. Upstream hoists in creation order: `ensureIdentifier` hoists the default-value temp when it creates `_a = source.x` (93654-93660), and `createVariableAssignment` hoists `cloneNode(name)` only when the `x = …` assignment is created (112728-112731). Rust's pre-pass `collect_declaration_list_hoists` (system.rs ~1040-1070) pushes the root temp and then every binding name via `collect_binding_name_nodes` before any element is flattened; per-element default temps are allocated later in `flatten_system_binding_element` → `ensure_system_binding_identifier` (2205), so they land after the names. Minimal change: for initialized declarations that go through the flatten, the pre-pass should only reserve the names (the `used_names` insert, so temp naming still avoids collisions) and the Identifier arm of `flatten_system_binding_target` (2081-2099) should push the hoisted name when it creates the assignment. Uninitialized declarations keep the pre-pass push, matching upstream `hoistBindingElement`. Root temps stay in the pre-pass; upstream allocates them before the element loop too. Adjacent control this also fixes: `export let { a = 1, b } = source;` expects `var _a, _b, a, b;`.

2. Missing `/** leaf */` before `_a = source.x` and its map. Upstream `createDefaultValueCheck(…, location = element)` (93612-93618) passes the BindingElement into `ensureIdentifier`, which does `setTextRange(createAssignment(temp, value), location)` (93660); the element's pos includes the comment, so the temp assignment prints it and maps at the element boundary. Rust `ensure_system_binding_identifier` takes no location and leaves the temp assignment synthetic. Fix: add a `location: Option<TransformNode>` parameter, `set_text_range(assignment, location)` when present, and pass `Some(element.original)` from `flatten_system_binding_element`. The pattern-level callers should pass the owning location as upstream does: the VariableDeclaration for the top-level call (`flattenDestructuringAssignment` sets `location = node`, 93251-93328) and `element.original` for nested patterns. Today those pass `None`, which also explains the "temp starts at the declaration position" observation. The `x = …` assignment already gets `element.original`, which is why the later two comments match.

Neither fix touches builtins.rs destructuring for CommonJS, the printer, or es2017.rs. For the replay, the four System rows should show `var _a, x;`, the first `/** leaf */` before `_a = source.x`, and the temp map at the element boundary; the 24 comment rows should lose exactly the leading `x` segment.
