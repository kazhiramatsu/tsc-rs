**Five distinct corrections; four are map-only with upstream lines, the `using` one is semantic and needs one discriminating probe before the fix site is chosen.**

**1. for-initializer / for-of-head / mixed-for maps (r53: `for-initializer` ES5+ES2015, `for-of-head`, `for-of-plain`, `mixed-for`).** Native's extra or shifted segments are all at the inlined head expression: a start map at the declaration list (`1:5 'var {'`) and an end map at the list end (`3:15`, `1:32`, `1:16`) that overwrites the last binding assignment's end map (TS keeps `3:5`, `1:22`, `1:15`, the element ends). Upstream `visitForInitializer` (112932-112948) returns `inlineExpressions(expressions)` bare; Rust `transform_for_initializer` ends with `set_original_and_range(expression, original)` on the list. Remove both halves: the range causes the maps, and the original would still feed the for-statement's `;` token cursor, which upstream anchors at `node.initializer.end` = −1 for the synthetic expression.

**2. array-default map.** TS maps `source` inside `source[0]` and `source[2]` at start and end (`3:17`, `3:23`) because `flattenArrayBindingOrAssignmentPattern` passes the reused parsed identifier straight into `createElementAccessExpression(value, i)` / `createArraySliceCall(value, i)` (93549-93558). Rust `flatten_system_array_binding` clones `value` per element; the clone is synthetic and unmapped. Use `value` directly for both the element access and the rest slice, as the object path already does.

**3. object rest ranges.** `createRestHelper` (25784-25818) is called with `pattern` as location (93523) and applies `setTextRange(createArrayLiteralExpression(propertyNames), location)`; `value` is passed unchanged. Rust `create_system_object_rest` clones `value` and ranges the excluded array to the rest BindingElement. Fix: pass the `ObjectBindingPattern` node into `create_system_object_rest` for the array range, and stop cloning `value`. Keep the rest element as the semantic original of the returned binding assignment, unchanged. The r53 rest rows currently fail on the late `__rest` definition (fixed in r51), so this range defect is masked until that rerun.

**4. import-after map.** TS maps `dep_1.value` at `1:37` to `1:42`, the import specifier's name. Upstream publishes through `getDeclarationName(decl)` (112814), which is `setTextRange(cloneNode(name), name)` (24788-24797); the print-time substitution to `dep_1.value` keeps that range. Rust `append_exports_of_import_binding` builds the access from a fresh generated identifier with no range. Fix: `set_text_range(value, local_name)` on the access returned by `create_import_binding_access`, nothing else.

**5. `export using resource = source` (semantic).** Upstream's ESNext pass emits a top-level `export let resource;` (`hoistBindingIdentifier` → `exportVars`, no export specifier and no `LocalName` flag) plus `resource = __addDisposableResource(...)` inside the try, whose target is `cloneNode(name)` with the parsed name as original. System does not learn the export from `exportedBindings` (upstream `collectExportedVariableInfo` only records `isLocalName` names, 92932-92934); it gets it from `getExports` → `getReferencedExportContainer(name)` returning the SourceFile for the exported `using` symbol, then `getDeclarationName(valueDeclaration)`. Rust mirrors the shape: `clone_binding_target` uses `clone_node`, which does set the original, and `exports_for_identifier` has the same fallback (`exported_from_source` → `exports_by_local`). So exactly one of two things is empty for this input: `get_referenced_export_container` on the clone's parse-tree name (checker/binder treatment of an exported `using` declaration as a module member, `emit_get_referenced_export_container_for_symbol` in checker/modules.rs:376), or `exports_by_local` for `resource` (module-info collection over the synthesized `export let resource;` whose declaration name is a clone). Do not fix by name spelling or by publishing nested declarations. Discriminate with three controls before touching either: `export let y = 1; y = 2;`, `export let y = 1; { y = 2; }`, `export let y = 1; try { y = 2; } finally { }`. If all three wrap, the defect is `using`-specific and lies in the checker/binder or the collection; if the nested ones fail, it is the execute-block visitor path. Then add `export using r = source;` at ES5, ES2015 and ESNext (ESNext keeps the declaration, so the ESNext row exercises `transform_hoisted_using_statement` instead), `export await using`, and `using` with an alias `export { r as s }`.
