**Verdict: the helper handling is the right minimal fix and matches upstream exactly; the BigInt fixture row does not test what its name says, and the shared predicates need only two one-line parity edits that no clean fixture can exercise.**

**1. Late helper requests in System.** Upstream `transformSystemModule` ends with `moveEmitHelpers(updated, moduleBodyBlock, helper => !helper.scoped)` (_tsc.js:112145) and never calls `readEmitHelpers()`, so helpers requested during its own flatten (`createReadHelper` at 25906 does call `requestEmitHelper`, as does `createRestHelper`) are left in the context and dropped; only helpers attached to the SourceFile by earlier passes are moved. No later transformer drains them for ES5+ targets. The tslib import is decided in `collectExternalModuleInfo` from attached helpers, and `__read`/`__rest` identifiers are qualified only through `EmitFlags.HelperName` substitution when `externalHelpersModuleName` exists. The Rust change mirrors all of it: `create_unscoped_helper_identifier` sets `HELPER_NAME | ADVISE_ON_EMIT_NODE` (factory.rs:5363), the System substitution hook (system.rs:148-175) qualifies through `get_external_helpers_module_name`, which is only set when an earlier pass recorded helpers, and no request is made. The fixture observations confirm both sides: `tslib_1.__read(source, 2)` and `tslib_1.__rest` only in the rows with an async arrow, bare `__read`/`__rest` with no declaration otherwise, and at ES5 the `__rest` declaration appears because the ES2018 pass requested it before System. Argument shape (`count` omitted only for a trailing rest, `0` for `[]`, `1` for `[,]`), `setTextRange(read, location)`, and `reuse = false` match 93534-93546. Name reservation and diagnostics: upstream reserves nothing for helper names and reports nothing; Rust likewise. Nothing overlooked there.

**2. BigInt.** Every default in the new row is `1n as any` / `1 as any`. The Rust TypeScript pass keeps an erased `as` as a `PartiallyEmittedExpression` node (builtins.rs:11520, 14752), and upstream does the same, so both defaults are non-simple and both get temps at every target. The observations show it: `_c = _b === void 0 ? 1n : _b` and `_e = _d === void 0 ? 1 : _d` at ES5, ES2015 and ESNext. The row validates PartiallyEmitted handling, not the BigInt exclusion. To discriminate, add a bare-literal row at target ESNext (legal for bigint): `export let {a: {b} = 1n, c: {d} = 1} = get();`, expected `var _a, _b, _c, b, _d, d;` with a temp only for `1n` (my r49 probe at ES2020/System). The System predicate is now correct for that row.

Shared predicates: `flatten_destructuring.rs:1815` and `es2018.rs:4773` still list `BigIntLiteral`; the other per-pass copies (builtins.rs:9852, es2021, both decorator passes, class fields) already use the upstream keyword-range form and need nothing. The two shared sites are reachable only when a bare bigint default meets a pre-ES2020 target (ES2015 or ES2018 host), which is checker error TS2737, so no clean fixture can cover them. Make the two one-line removals for parity with `isSimpleCopiableExpression` (93027-93032) or leave them recorded; either way do not claim coverage.

**3. Two small notes for the replay.** The `[,]` row now emits normally because the control uses `get()`; keep the r47b receipt as the record that the bare `source` form crashes upstream. And the ES5 profile of the bigint row hoists `_a … _e` before `b, d` because the ES2015 pass's own `var` statement is hoisted first by System's uninitialized-declaration path, the same cross-pass dependency noted in r49.
