## r29 findings

### 1. Empty single-line block comments (`{  /**/}` vs `{ /**/ }`)

**Cause confirmed in printer.rs `emit_empty_block_comments` (17607-17648).** The single-line branch writes the list space first, then `emit_empty_node_array_boundary_comments` (18280) writes the open-brace trailing comment with its own prefix space and never writes the list space that upstream puts *after* the trailing phase. Upstream `emitBlockStatements` (_tsc.js) orders: open-brace token + `emitTrailingCommentsOfPosition(pos, prefixSpace=true)`, then `emitList(SingleLineBlockStatements)` whose empty branch writes one space, then close-brace leading comments. So `{` + ` /**/` + ` ` + `}`.

**Codex's fix is the right shape.** Generalize `emit_empty_multiline_block_boundary_comments` (18330) with a `multi_line` argument: keep its suppression loop unchanged; for multi-line keep `write_line` + indent + leading comments; for single-line write one `write_space(" ")` between the trailing loop and `emit_source_leading_comments_of_position`. Route both layouts of `emit_empty_block_comments` through it and remove the pre-space at 17645. Leave `emit_empty_node_array_boundary_comments` for its other callers (empty parameter/argument/element lists), whose upstream `emitList` has no `SpaceBetweenBraces`.

**Function-body suppression is consistent with tsc, verified by probe.** `function f() { /*a*/ }` prints `{ }` (same-line comment after the brace dropped), `function f() { // a\n}` prints `{\n}`, while `{\n    /*a*/\n}` keeps the comment; statement blocks keep same-line comments (`if (x) { /*a*/ /*b*/ }`, `{ /*a*/ }`). The existing `suppress_same_line_trailing` flag models this, so the generalized helper must keep skipping suppressed comments in the single-line case and then still emit the list space (yielding `{ }`).

**Controls (complete commands, ES5 and ESNext, removeComments off/on, maps on):** `for (let f in o) { /**/ }`, `if (x) { /*a*/ /*b*/ }`, `while (x) { // a\n}`, `if (x) {\n /*a*/\n}`, `{ /*a*/ }`, and function/arrow/method bodies in the same three layouts (expected `{ }`, `{\n}`, `{\n    /*a*/\n}`). With removeComments the empty branch returns false and the plain `{ }`/`{\n}` path must stay unchanged.

### 2. H2.6c retired migration row

**Why it fails.** `h2_6c_refusal_migrations::validate` (69-140) requires `listed.entries.get(row.case_id)` to hold the retained `outFile` vector, and the manifest is now absent. Even if it were present, the registry executor at h2_2c_acceptance.rs:5129-5158 would return `Ok` for this row and `partition` (200-235) would reject a registered row that compared successfully. The migration registry can only describe a row that is *still refused*; this row is not.

**Smallest robust change: move the row from `refusal_migrations::CURRENT` to `h2_6c_de_promotions::CURRENT`.** That registry is the designed end state for "old input refused, current D/E input exact": it pins `old_case_sha256`/`old_input_sha256` (frozen H2.6c qualification), `new_input_sha256` (frozen h2-7de census/inputs/observations, sha-pinned at 1987-2001), `old_refused_option`, and measured `c/d/e_requests` plus `declaration_members`, and `validate_results` (2119-2160) demands exact twice under the unchanged comparator. Nothing substitutes inputs silently: both identities are named in the row. `validate` also refuses a row present in both registries, so the migration row must go. `validate_results` tolerates an absent prior vector (`if let Some(previous) = listed.get(...)`), so the deleted manifest is fine. Owner projection: `required_slices` must equal `["H2.7d"]` (d=1,e=0) or `["H2.7d","H2.7e"]`; check the frozen census row (`h2-7de-candidates.v1.json`) before choosing the counters, and note the old migration pinned owners `["H2.7d","H2.8b"]`, which `de_promotions::validate` would not accept; if the census says H2.8b, the owner match at 2035-2040 needs an `H2.8b` clause analogous to the `OUTPUT_DIRECTORIES` push, backed by the census, not by editing the census.

**Counters.** `h2_6c_refused_option_totals` (5555-5597): the projected map is adjusted by promotions and migrations in sequence. Today `outFile 171 → 170` via the migration and `useCaseSensitiveFileNames +1`. After the move: `de_promotions::adjusted_refusals` subtracts one from `old_refused_option` (`outFile 171 → 170`), no `useCaseSensitiveFileNames` bucket, and `h2_6c_refusal_migrations::count()` becomes 0. Expected live totals therefore lose the `useCaseSensitiveFileNames: 1` entry; nothing else moves. `pre_flip` stays historical.

**Keeping the mutation tests non-vacuous.** `de_registry_contracts.rs` asserts both `promoted_count() > 0` and `refusal_migrations::count() > 0` (20-27) and builds `migrations` from registered rows. With CURRENT emptied, the honest change is to make the migration-specific tests conditional on `count() > 0` while the promotion tests stay unconditional, and to keep a synthetic in-memory `Migration` fixture for the identity/fingerprint rejection paths (`populated_registry_identity_and_error_fingerprint_reject_mutations`, `populated_partition_*`) so those still execute. Deleting the module or leaving a fake live refusal would either drop coverage or misreport the current state.

**Other stale pins from the two corrected oracle rows.** The three case-sensitivity rows (`sourceMapWithNonCaseSensitiveFileNames`, `…AndOutDir`, `sourceMapWithCaseSensitiveFileNamesAndOutDir`) appear only in `EF3_ROWS` (emitter_final_rows.rs:54-63, still 8 rows, already exact x2) and in the deleted manifest; no other registry names them. The `h2-7de-*` artifacts are sha-pinned in both `de_promotions::validate` and `refusal_migrations::validate`; if the oracle refresh regenerated any of them, those three hashes must be re-pinned in the same change, otherwise `validate` fails before reaching the row logic.
