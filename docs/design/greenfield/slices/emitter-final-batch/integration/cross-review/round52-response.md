**Root causes confirmed from the r52 record (native vs TypeScript, JS and maps).**

**1. ES2015 `super.m()` (4 rows): only the map differs, and the extra segment is the call's end.** Native adds gen 20:88 ← src 0:85, the position right after `super.m()`; TypeScript has none. Upstream `substituteCallExpression` (101514-101527) builds a fresh `createCallExpression` with no `setTextRange`, and because Substitution precedes the Comments/SourceMaps phases the synthetic call has neither a map nor a comment phase; only the inner access is ranged (101493-101503). Rust `visit_captured_super_call` ends with `set_original_and_range(call, original)`. Drop that call entirely and return the bare call: the range produces the end map, and the original link would still feed `original_node_end_cursor` for any parent token (a `.x` after `super.m()`), which upstream never sees. Keep the inner property/element donors as decided in r45. Nothing downstream needs the call's original at ES2015+; the ES5 route never reaches this function.

**2. ES5 `super /*a*/\n . /*b*/ x` and `super[/*a*/ 'x' /*b*/]` (4 rows): JS differs, same single cause.** TypeScript prints `_super.prototype /*a*/.x` and `_super.prototype['x' /*b*/]`; native prints `. /*b*/x` and `[ /*a*/'x'`. The ES2015 pass replaces `super` with `_super.prototype` carrying `setOriginalNode`, `setCommentRange`, `setSourceMapRange` (107956-107961, mirrored at es2015.rs:3193-3215) but no text range. Upstream then emits the dot and bracket tokens with `emitTokenWithComment(token, node.expression.end, …)` (118223-118247, 118268-118274): `node.expression.end` is the raw end, −1 for the synthetic receiver, so no leading or trailing-of-position comments are claimed for the token, and `/*b*/`/`/*a*/`, being same-line comments after the token, are not leading comments of the name/argument either (the `iterateCommentRanges` collecting-after-newline rule). Rust derives the token cursor from `original_node_end_cursor(expression)` (printer.rs:7472 for the dot, 7602 for `[`), which follows the receiver's `original` to the `super` keyword's end, so the fixed-token emitter walks from there, finds the token in source, and claims its trailing comment with the `emitTrailingComment` prefix space. The maps show it: native has an extra comment segment (gen 68:62 ← 1:3 for `/*b*/`, gen 67:52 ← 0:71 for `/*a*/`).

Smallest semantic-owner fix: in those two arms use the raw `node_end_cursor` (printer.rs:16779, whose own doc already records that fixed tokens anchor at `node.expression.end` after transformation) instead of `original_node_end_cursor` for the receiver. Synthesized receivers then yield a `Synthetic` cursor, exactly upstream's −1. The trailing-anchor dedupe still works because a receiver with a raw range is unchanged, and a synthetic receiver's own comment phase (`/*a*/` via its `comment_range`) is unaffected. Do not touch `visit_super_keyword`'s donors; they are upstream's. Leave the other 27 `original_node_end_cursor` sites alone; they anchor tokens after parsed children where raw and original coincide.

**Controls to add.** ES2015 (both modules, both removeComments): `return super.m() /*c*/;` (comment dropped upstream, no end map), `super.m().x` (dot after a synthetic call), `super.m /*c*/ ();` (comment stays after `_super.m`), `super[k]();`. ES5: `super.x /*t*/;` (name's own trailing phase), `super\n .x` (no break, already present), a non-async `m() { return super.x; }` witness to show ordinary ES5 super output is unchanged by the cursor change, and one class-field receiver with a set text range, `(_a = obj).method /*c*/.bind(_a)` style, to show raw-ranged synthetic receivers still claim their dot comments.
