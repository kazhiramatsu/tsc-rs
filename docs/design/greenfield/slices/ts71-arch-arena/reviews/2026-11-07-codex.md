# Arena rewrite: adversarial design review

## 1. Verdict

**NO-GO for implementation against the document as written.** The approved direction does not need another approval; the storage contract and the claimed economics need correction before the three implementation PRs begin. A copyable handle cannot safely manufacture a static reference to a releasable arena; shared frozen binder symbols cannot contain checker-specific writable table pointers; old snapshots cannot support the proposed in-place incremental mutation; and several proposed identity, cache-key and diagnostic changes contradict existing observable contracts. The records establish a distributed cost problem, but do not establish that this particular rewrite removes the roughly 42 G needed for normal-build parity. Replace the asserted endpoint with a hypothesis, resolve the trust-path findings below, and start with a bounded vertical feasibility slice before freezing the shared APIs or committing the full schedule.

But the document must distinguish the true instantiated allocation shape from ordinary transient clones. `create_symbol_with_type` retains a target while copying independent declarations/parent (`C/structural.rs:6613–6645`); target presence is not proof of shared-data eligibility. Require read/write dispatch and flattening rules, retained origin ownership and an audit of these mutation sites. Forwarding every mutation to an origin, or forwarding reads while writes update an invisible local copy, changes semantics. The instantiated record also has a different field layout from today's `Symbol` (`crates/binder/src/symbols.rs:27–52`): `symbol(id) = id.get()` cannot preserve direct `name/parent/value_declaration` field access by itself. Specify a symbol view/accessor migration and price the new origin reads.

The tax that remains includes the binder's complete syntax/flow walk, global/pattern merging, request normalization and resolution, per-Program source facts, per-checker caches on shared syntax/symbols, list-content interning and hash probes, required semantic snapshots, and mutable partial-state protocols. Some reads are already direct: `TypeTables::type_of` and `SymbolArena::symbol` (`crates/types/src/tables.rs:1010–1018`; `crates/binder/src/symbols.rs:587–599`). Owner-qualified access also still needs an ownership proof even if the hot dereference is cheap. These costs can be reduced, but none vanishes merely because the payload has a stable address. The two rejected structural prototypes reinforce the need to price the exact mechanism: their VS Code wall medians were +0.28%/+0.09% for syntax sharing and +0.61%/+0.83% for flow indexing (1/4 threads), not evidence that a larger rewrite will succeed or that all structure changes are futile (`docs/design/greenfield/slices/ts71-perf-tsrs/STRUCTURAL-2026-11-07.md:86–106`).

## 5. Alternatives

There is **no evidenced cheaper route to the same full parity outcome**. These two subsets can establish useful wins and reject expensive assumptions sooner; neither deserves a parity promise.

1. **Keep the immutable syntax/store contract initially; replace the hot checker ownership boundaries as one vertical batch.** Use the existing owner-qualified frozen/claimed primitives for completed type lists, signature/member lists and the true instantiated-symbol population; pass canonical list keys through consumers and keep mutable partial data versioned. Keep semantic ordinals distinct from placement. This addresses the dominant semantic gap without simultaneously replacing parser, API decoder and emit identity. Evidence: semantic was 58% of B0's gap; B-2 gives actual site/length distributions; B-3 gives signature/tail and transient populations; the remaining S2–S11 items were not all implemented (`P:303–308`). Estimated cost: **one to two weeks for a bounded compiling/economic pilot, then re-estimate**. Low-single-digit instruction improvement is an investigation hypothesis; the old 5–9% whole-program plan is not a new measurement. This is a coherent subset, not another sequence of one-field tweaks.

2. **Qualify PGO and final-placement front-end construction before changing every record family.** Keep existing immutable consumer views and deterministic logical IDs; prototype removing the real relocation/copy boundary while retaining graph finish, metadata and required normalization. Qualify PGO on the current source with held-out workloads and fixed build identities. Evidence: the prior track leaves FE4 and PGO unimplemented; historical PGO is material, whereas relocation exposure is only a few G and not all recoverable (`P:297–310,1303–1326`; `H/tsrs-layouts-report.md:45–55` describes distinct physical placement and payload views). The owner already rejected standalone FE4 for an expected 3% (`P:272–274`); do not silently reopen that track. Use it only as a bounded feasibility question within the approved rewrite. Estimated cost: **several days to qualify the PGO pipeline plus a one-to-two-week final-placement prototype**, not a complete production migration. A transferred 13–14% PGO reduction alone gives **109.8–111.1 G** from 127.7; even a separate 3% normal FE gain would leave roughly **106.5–107.8 G PGO**, above tsrs's 75 G. The value is early decision evidence, not a disguised solution to the remaining gap.

## 6. Questions for the owner

1. When the feasibility results arrive, is continuation contingent on a credible **normal-versus-normal parity** path, or is a substantial memory win with a smaller instruction gain acceptable? Specify the tradeoff before the full freeze is spent.
2. Is 32 GiB a supported **process-wide hard limit**, including multiple live Programs, or must the architecture support larger/churning service workloads? This determines the overflow/reuse contract, not merely an allocator constant.
3. Must wasm32 remain a supported production target through this rewrite, with an explicit smaller memory limit, or may its backend be deferred? A native 32 GiB contract cannot answer that decision.
4. Should the 8–10-week freeze be a provisional envelope re-estimated after the vertical slice, or a fixed delivery constraint that requires narrowing scope? The current document promises both breadth and an unqualified mechanical migration estimate.

These are scope/acceptance decisions. The team can resolve field layouts, owner-qualified APIs, CI wiring and test selection without asking the owner to design them. The approved rewrite direction and fidelity requirement are already established.
