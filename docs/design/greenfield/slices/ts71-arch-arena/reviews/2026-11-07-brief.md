## What to attack (answer every numbered item; add your own)

1. **The diagnosis.** The document claims the 1.5× is an architecture tax (routing, side tables, links indirection, ownership
   copies, two-phase construction) that disappears under the arena model, and cites tsrs's 85.5 G as the ceiling proof. Is that
   supported by the ledgers, or does the evidence point elsewhere (e.g. the Codex consult's "distributed state-management overhead",
   the A-1a lesson that a smaller record added 3.4 G, the relocation delta that was 0.25 G against a 1.0–1.3 G forecast)? Which
   parts of the tax are NOT removed by this design?
2. **The memory model.** `Ref<T>` = NonZeroU32 × 8 bytes over one 32 GiB reservation; `Ref::get() -> &'static T`; `&self` allocation
   with `Cell` bump; `ArenaCell` for mutable fields; per-checker contiguous reservation so that handle order = creation order; 64 KiB
   blocks and a block-owner table for `source_of_node`. Find the unsoundness, the aliasing/`&mut` conflicts with the existing
   `&mut self` checker (192 K lines), the speculation-journal leak (links.rs has 117 journaled `set_*` entry points; see
   speculate.rs), the multi-Program/LSP lifetime problems (`Ref::get` with a released arena), the wasm32 story, and the 32 GiB cap.
3. **Fused parse+bind in the loader worker.** Check `crates/program/src/loader.rs` (`load_task`, `admit_source`,
   `bind_existing_source`, `finish`) and `crates/binder/src/declare.rs` for what bind needs that is only known after loading
   (options, impliedNodeFormat, content mappers, JSON, lib files, project references, `commonJsModuleIndicator`, pattern ambient
   modules, `classifiable_names`, the global symbol merge). Is the fusion possible without changing tsgo-observable behavior?
4. **Inline binder fields in node tails.** The design moves `BindData`'s per-node maps (symbol, locals, local_symbol, next_container,
   flow, end/return flow, when_true/false, possibly_exhaustive, fallthrough, binder-written NodeFlags) into kind-specific tails.
   Check against tsgo's `ast.go` node data structs which kinds carry which binder fields; find kinds the document would get wrong
   (e.g. nodes that get a flowNode without being an Identifier/this/super/expression kind; locals on kinds that are not
   containers). What does the emitter's "modify a detached copy" do today that conflicts with an immutable, binder-written tree?
5. **Checker records.** Type header 24 B + kind tails holding both payload and links; transient symbols 32 B instantiated form with
   `origin`; Signature 48 B + rare; StructuredMembers 32 B; persistent links as 2-level page tables. Check `crates/types/src/ty.rs`
   (TypeData variants), `crates/checker/src/links.rs` (NodeLinks/SymbolLinks/TypeLinks and the 37 cold maps), `state.rs`
   (Signature 136 B fields, ResolvedMembers) and tsrs's `types.rs`. Which fields does the document forget, which cold maps cannot be
   made tails, where would a tail make a type bigger than today's 40 + 24 B, and does `origin`-based transient symbol reading break any
   caller that mutates a transient symbol's declarations/parent/name (count the sites)?
6. **The borrow argument.** "Arena is `&self`, mutable fields are cells, therefore `to_vec` (296) and `clone` (531) can go." Sample
   30 of those sites in `crates/checker/src` and classify: borrow-forced copy / semantic snapshot / small inline copy / other. Is the
   expected saving (several G) credible given the B-2 dynamic census (most copies inline ≤ 8 elements, 369 MiB total logical payload)?
7. **The gates and stop rules.** Front end ≤ 20 G after phase 1 (today ≈ 29 G at B0 minus what landed since), semantic ≤ 75 G after
   phase 2, stop at 22 / 80 G. Are these the right numbers and the right places? Is the M1 ledger method (proc_pid_rusage at phase
   boundaries) usable on the new code, and how should "front end" be delimited once parse and bind are fused? What gate is missing
   (e.g. LS incremental correctness, API wire identity, project references, `--build`/watch, declaration emit, JS/JSDoc files)?
8. **The migration mechanics.** The `NodeData<'a>` view enum keeping variant and field names so that 8,400 `NodeData::` match sites
   compile; Box deref sites; `NodeLookup`; `kind_of` 1,758 sites; `source_of_node` 453 sites; emitter's factory. Estimate from the code
   where the view-enum trick fails (patterns that take `&NodeData` by value, store it, compare it with `==`, or mutate it:
   `set_data`/`reshape`/`node_mut` users). Is the 500–800 hand-fix estimate credible? Where will the borrow checker fight the
   `&'a XxxTail` views inside `&mut self` methods?
9. **Expected numbers.** Front end 15–18 G, semantic 68–74 G, total 85–95 G normal / 76–85 G with PGO, peak 1,900–2,200 MiB. Rebuild
   the arithmetic from the ledgers and tsrs's rows. Where is the document optimistic, and what would you put instead? Is "parity with
   tsgo fidelity, +5–10% from front-end fusion/SWAR/u32 names/PGO/placement" the right expectation?
10. **The order and staffing.** Phase 0 → 1 → 2 → 3, three Codex lanes in parallel on a shared crate API, one integrator, a feature
    freeze of 8–10 weeks, three large PRs. What ordering would reduce risk (e.g. checker data layer first because it is 58% of the gap;
    or a thin vertical slice through all layers first)? What should be prototyped in a throwaway build to de-risk before phase 1?
11. **What is missing from the document entirely.** List items the plan does not mention that the rewrite will hit (crates: api, ls,
    lsp, project, incremental, harness, conformance, emitter/declarations; features: JSON files, JSDoc, content mappers, project
    references, `--build`, watch, the API's node/symbol handle registry, the fingerprint oracle's assumptions, CI job selection).
12. **A cheaper route to the same outcome?** If you believe a different architecture (or a subset of this one) gets most of the win
    at a fraction of the cost, say so with the mechanism and the evidence. Maximum two alternatives.
