# Adversarial review: arena rewrite of scanner/parser/binder/checker (Opus 5.5, 2026-11-07)

Document under review: `docs/design/greenfield/slices/ts71-arch-arena/README.md` at main `aa1992224` (cited as `D:<line>`).
Method: read-only. grep/wc/python counts over the tree at `aa1992224`, the packet ledgers and the H/ and G/ roots. No cargo, compiler,
benchmark or profiler was run. Time box about 90 minutes. Every number I derive is marked "derived"; ledger numbers keep their row.

## 1. Verdict

**NO-GO as written; GO WITH CHANGES after a one-week phase 0b.** The direction, ending identity rewriting and publication and
moving the binder outputs and checker records into owner arenas, is reasonable, and some of it is tsgo-faithful (tsgo binds right
after parse in its own parse cache, `G/project/parsecache.go:78-80`). The document is not ready to freeze main for 8 to 10 weeks,
for four reasons:

- The memory model is unsound as specified: a safe `&'static T` from releasable, heterogeneous, cross-thread blocks with cells.
- Its gates are anchored to a stale, unmeasured baseline, using an instrument that is not in main.
- Its expected numbers cannot be rebuilt from the ledgers. My arithmetic puts the phase-1 front end at 21 to 28 G against a
  ≤ 20 G gate, so the stop rule is likely to fire by construction.
- It plans neither the emitter's tree-copy model (which depends on the remapping it deletes) nor determinism across worker
  counts once bind moves to the loader workers.

The premise ("the tax disappears all at once") was never tested by the one-day ceiling experiment the 11-04 consult proposed, and
no record of it exists. Run that, a measured B1 anchor and a throwaway front-end prototype first (≈ 5 to 7 person-days), then
re-derive the gates.

## 2. Findings

### BLOCKER

**B1 — §0 principle 1, §2 0.1, §3 1.4/1.7, §9 (memory model soundness).**
- *Claim.* `Ref::get(self) -> &'static T` (D:76-77); arenas allocate with `&self` and a `Cell` bump (D:80-81); mutable fields are
  `ArenaCell` (D:84); `Arena::release()` does `madvise(MADV_FREE)` for emit arenas and old LS trees (D:87); "arena の生存は持ち主の
  `Arc` が保証" (D:77).
- *Evidence 1: release makes a safe `&'static T` dangle.* `Ref<T>` is a `Copy` u32 with no tie to the `Arc`. After `release()`,
  and after block reuse if blocks are recycled, a stale `Ref` reads arbitrary bytes as `T`. Today's store is memory-safe only
  because each region holds one record type and "an all-zero record ... is a valid value, so a stale identity reads an empty
  record rather than a dangling one" (`crates/store/src/lib.rs:31-38`, `get` at :129-139). The design's 64 KiB blocks mix node
  kinds, symbols, lists and tables, so that property is gone. A garbage `kind u16` feeding the `data()` jump table (D:102) is
  undefined behaviour, not a logic error.
- *Evidence 2: cross-thread data race.* `Ref<T>` is auto `Send + Sync`, so any thread can deref a checker-arena `Ref` whose record
  holds `ArenaCell`s (`!Sync`) while the owning checker writes them. Today a `TypeId` cannot be dereferenced without the
  checker's tables.
- *Evidence 3: the document contradicts itself.* "freeze 後の書き込みは debug で panic" (D:82), yet 1.7 updates old frozen file
  arenas in place (D:191), and 1.4 swaps "symbol の `tables` cell" for late-bound and merged tables (D:161-162). The code enforces
  the opposite today: "file binders are read-only after bind ... merge writes go to transient clones"
  (`crates/checker/src/program.rs:1260-1270`, `unreachable!` on a file symbol).
- *Evidence 4: exhaustion versus reuse.* If released ranges are never reused, 32 GiB is a hard ceiling for long LSP and watch
  sessions. Each new Program version needs fresh checker ranges (VS Code checker data is about 1.5 GiB per full check, consult-opus
  §1.7), so the derived limit is roughly 20 full re-checks. If ranges are reused, Evidence 1 applies.
- *Evidence 5: order rests on unsized contiguity.* `Arena::contiguous(bytes)` (D:81-82) is unsized, and wasm32 cannot reserve
  (D:332). Yet type order is defined as address order (D:52-53, D:212-213), which is on the trust path through `compare_types`
  and union order.
- *Proposed change: add a "soundness model" section to phase 0.1 that fixes the following before any lane starts.*
  - (a) Deref goes through a capability. Either `Ref<T>::get(&'a ArenaView) -> &'a T`, or `'static` only for CLI arenas that are
    never released (tsrs leaks its arenas; handover §7). LS and emit arenas use a lifetime-branded `Ref<'a, T>`.
  - (b) Shared file arenas contain no cells. The binder writes through the builder's exclusive `&mut` before `freeze()` returns
    `Arc<FrozenFileArena>`.
  - (c) Checker-arena `Ref`s are `!Send`, or carry the checker id and are checked in debug.
  - (d) Released ranges are retired (`PROT_NONE`), never reused for a different owner. State the LSP address budget.
  - (e) Order types by a dense per-checker `id: u32` in the Type header (tsgo `t.id`; tsrs also keeps `id` in its header,
    handover §7), not by address. This removes the contiguity requirement and also fixes B5.
  - (f) Add trybuild and Miri tests for these rules in `crates/arena`.
  - (g) Delete 1.7 (see M1) and restrict `tables` swaps to transient clones.

**B2 — §1 table, §3/§4 exit gates, §8 (baseline and instrument).**
- *Claim.* "今（#913）" is 127.7 G and 2,886 MiB, with front end ≈ 29 G and semantic ≈ 95 G (D:308-313). Gates are ≤ 20 G and
  ≤ 75 G "M1 台帳で" (D:197, D:269).
- *Evidence 1: the numbers predate #911 and #913.* 127.7 G and 2,886 MiB are "+ #909・#910 の card の実測の和。anchor ではない"
  (packet 終了 table, README:282). After them, #911 cut VS Code peak footprint by −7.25% (1 thread; packet 再評価 table) and #913 cut
  instructions by about −0.74%. Derived current peak ≈ 2,886 × 0.9275 × 0.9988 ≈ **2,674 MiB**, which is already the document's
  "段 1 後 ≈ 2,650 MiB".
- *Evidence 2: the instrument is not in main.* `grep TSRS_PHASE_LEDGER|proc_pid_rusage crates/*/src` returns nothing. The M1
  instrument is an unmerged observation patch on B0 (`m1-lane-record/`).
- *Evidence 3: the split is unmeasured, and my reconstruction disagrees.* B0 front end = load 24.69 + pub/adopt 4.12 + bind
  9.29 = 38.10 G. Measured front-end cards since then: #891 ≈ −1.18, #893 ≈ −1.12, #896 −1.55, #897 −0.53, #900 ≈ −0.65, plus
  #894/#895 ≈ −0.4, for ≈ −5.4 G. That gives front end **≈ 32.7 G**. Finalization fell 0.92 G with #890, so semantic is ≈ 93.2 G
  at #910 and **≈ 90–92 G** after #911/#913. Uncertainty is ±2 G either way, but both of the document's figures are off by
  about 4 G, in opposite directions.
- *Evidence 4: fusion makes the boundary undefined.* Once parse and bind are fused, the B0 boundaries load / pub+adopt / bind no
  longer exist.
- *Proposed change: add phase 0b "B1 anchor".*
  - Land the M1 ledger on main behind a `phase-ledger` cargo feature at #913.
  - Define front end architecture-neutrally as [program creation start → checker-init start].
  - Measure tsc-rs #913 and tsrs in one quiet window (warm-up 2, 9 rounds), plus peak.
  - Restate every gate and stop rule as a delta from B1 with component budgets (see B3).
  - Never change the instrument in the same PR as the subject.

**B3 — §0 diagnosis, §8 numbers, phase-1 gate (unsound cost estimate; gate unreachable by its scope).**
- *Claim.* Front end goes 15–18 G after phase 1 ("tsrs の 17.6 G を下回れる唯一の段", D:49) and semantic 68–74 G after phase 2;
  "構造を替えれば一斉に消える。tsrs の 85.5 G がその上限の実測" (D:18-19).
- *Evidence, front end.* What phase 1 can remove (derived from B0 rows and the cards since):
  - publication/adopt ≤ 4.1 G (60% is `relocate_with_leases` ≈ 2.3 G; `validate_canonical_case` and `add_module_resolution`
    ≈ 10% of the bucket stay; ledger "FE4 の内訳").
  - request walk ≈ 0.4–0.6 G (≈ 0.8 G left after #891 against tsrs 0.19).
  - parse ≈ 0.8–2.3 G (≈ 12.4 G now against tsrs 8.4; the byte scanner and inline finish have already landed).
  - bind ≈ 0.5–1.5 G. The per-node tables are already position-keyed with no routing (handover §4.6), so moving them inline
    saves memory, not instructions; only the hash maps (locals, next_container, end/return flow) and the Box/Arc tables cost
    instructions.
  - Total ≈ 5.2–8.5 G, giving **21–24 G from the document's 29 G, or 24–28 G from 32.7 G**.
  - Outside the scope: resolution (B0 4.08 vs 1.88 G, 2.17×), fs/loader (4.18 vs 2.99 G), and name interning at parse (tsrs
    rejected a global interner at parse +9%).
  - Fusion buys cache locality, which is wall time, not retired instructions. The gate measures only instructions.
- *Evidence, semantic.* The mechanisms the design removes were partly priced:
  - S3 lane (routing removal by node flag and `NodeLookup`, 2-level `NodeLinks`): **−0.91%** against a −1.0 to −1.9% forecast.
  - F10b (global flow id): −0.27 G in total.
  - D1 (relocation by deltas): −0.25 G against −1.0 to −1.3 G.
  - A-1a part 2 (smaller node): **+3.40 G**.
  - node_symbol compaction: **+855 M** from about 48 extra instructions per read.
  - B-2: 53.6 M list copies and 369 MiB of copied payload, mostly ≤ 8 elements, so the copy cleanup is worth ≈ 1.5–3 G.
  - Codex's largest bucket, "relation/member/inference control paths ... repeated queries", is 8–16 G
    (`consult-codex-2026-11-04.md:76`). A data layout does not touch it. The profile has `choose_overload` at 40% inclusive, and
    the flow memo rejects 1.61 M of 2.59 M key hits by epoch.
  - tsrs builds 8.1% fewer types; the fidelity tax is about 3–5 G.
  - A tsgo-faithful "tsrs-equivalent" semantic is therefore ≈ 70–72 G. The document's 68 G would beat it.
- *Evidence, premise never tested.* The 11-04 consult's "天井の実験" (bump global allocator + dense unchecked links,
  `consult-opus-2026-11-04.md:108-117`) was scheduled as M3 (`RESUME-integrator.md:51`). No m3 or ceiling record exists in
  `H/` or in the packet.
- *Proposed change.*
  - Replace the expectation table with a component ledger: mechanism × N × instructions per operation, with B1 as the base.
  - Set the phase-1 gate from that ledger. Example: B1 − (5 to 8) G, or include resolution/fs in phase 1 with its own budget.
  - Add a wall-time gate (1 and 4 threads) for what fusion and layout claim to buy.
  - Gate the start of phase 1 on phase 0b: the ceiling experiment (≤ 2 days, throwaway) and a throwaway front-end prototype
    (parse into the final arena + inline binder fields + no publication, run only through parse+bind+fingerprint on VS Code).
  - Proceed only if the ceilings show phase 1 front end ≤ B1 − 6 G and phase 2 semantic ≤ 80 G.

**B4 — §3 1.6, §5 3.1, §10 (emitter and node builder; trust path: emit and diagnostic text).**
- *Claim.* The emitter needs "3 人日" (D:274-276); `relocate.rs` is deleted and not generated (D:103, D:151); consumers compile
  unchanged through a view enum of `&'a XxxTail` (D:104-105, D:184-187).
- *Evidence.*
  - `TransformArena::add_source` copies the whole parsed `SourceFile` and detaches it (`crates/emitter/src/factory.rs:465-468`),
    then maps back to parse ids by base arithmetic (`parsed_node_base/parsed_node_end`, :463-473).
  - `remap_node_data_ids` is called at `factory.rs:7937`. `copy_subtree` is used by `synthetic_file.rs:148`.
  - With global `Ref` addresses a copied tree's child links must be rewritten, which is exactly the relocation the design deletes.
    Base arithmetic no longer maps copies to originals.
  - The emitter mutates nodes in place: `node_mut` 14 sites and `set_data` 4.
  - At least 94 single-line plus 28 multi-line `NodeData::X(XData {…})` constructions in the emitter, and ≥ 101 in the checker's
    node builder, build node values. A view enum of references cannot construct a value.
  - The node builder feeds `typeToString` in diagnostics, so diagnostic text is on this path.
  - `diffout.py` compares only exit/stdout/stderr (`target/claude-tools/perf11/diffout.py:20-30`). Emitted `.js`/`.d.ts` bytes are
    checked only by hosted conformance, and phase 1 changes the emitter's input.
- *Proposed change.*
  - Generate `deep_copy_with_remap(src, root, dst) -> (NodeId, OriginalMap)` (tsgo `DeepCloneNode`) and keep the detached-copy
    model on it.
  - Give the emit arena an explicit original-node side table.
  - Add owned `XxxData` builder structs for the construction sites.
  - Budget 8–12 person-days.
  - Add to the phase-1 exit an emitted-file identity check (all output files) on hono/zod/vue/TypeScript `bench-emit` and
    `bench-decl` against #913.

**B5 — §5 3.2, §9 (API wire identity).**
- *Claim.* "API の node/symbol handle は登録制の opaque 値なので wire 不変" (D:277-278).
- *Evidence.* Type handles are not registered values: `fn type_handle(ty) -> u32 { ty.index() + 1 }`, "tsgo `TypeHandle`: the
  checker's number of the type" (`crates/api/src/checker.rs:1471-1474`). With `TypeId = Ref<Type>` (D:92), `index()` becomes a
  byte offset divided by 8, so every type handle on the wire changes and stops matching tsgo's dense ids. Symbol handles are
  registered (:1291-1299), and node handles are table indices (:1791-1805), so those two are fine.
- *Proposed change.* Keep a dense per-checker `id` in the Type header (same as B1(e)). Make `type_handle` use it. Run the API
  suite at the phase-2 exit, not only phase 3.

**B6 — §3 1.5 and its gate (output determinism across worker counts).**
- *Claim.* Bind moves into the loader worker right after parse (D:174-175). The phase-1 gate is 1-thread 8-project identity plus
  2 shuffle seeds (D:196-198).
- *Evidence.*
  - Today symbol ranges and private-name serials are reserved **serially in Program order** before the parallel bind, "so the
    identities are the same for every budget" (`crates/checker/src/lib.rs:6214-6262`; `get_symbol_id` lazily assigns from a
    counter, `crates/binder/src/declare.rs:696-707`).
  - With bind at discovery time on arbitrary workers, allocation order, `SymbolId` values and serials depend on scheduling.
  - The shuffle harness permutes block addresses but never varies the worker count or schedule.
  - DET-1 (#905) established default-thread determinism with 5 runs × 8 projects. Phase 1 changes exactly the parallel part, but
    its gate tests only 1 thread.
- *Proposed change.*
  - State how private-name serials and binder symbol ids are assigned at discovery time (file-local plus Program-order fix-up, or
    lazily in the checker as tsgo does).
  - Add to the phase-1 exit: workers 1/4/default × 3 runs × 8 projects, identical stdout/stderr/exit, plus the
    Types/Symbols/Instantiations/Identifiers/Nodes rows.

- **M10** §1 order: front end first forces every consumer (emitter 62 K lines, LS, API, fingerprint tool) to change in PR #1 for the

- **M11** §5 3.3: finalization is stale. #890 already removed 0.92 G of the 1.23 G (ledger row "1 checker の CLI 経路の後始末"). Change:

- **M12** §3/§4 gates: missing gates. The LS suite (4,583) and API suite run only at phase 3, although phase 1 changes trees, NodeIds and

- A rollback plan if phase 2 misses: the document has "2 PR に分ける退路" but no instruction on what main keeps if phase 1 has landed
  and phase 2 is abandoned.

## 5. Alternatives (at most two)

**A1 — Checker-first arena, front end by FE4, PGO now.**
- *Mechanism.*
  1. Land PGO in release (measured −18 to −21% instructions on tsc-rs, slice 8).
  2. Move the checker's own records (types with a dense id, transient symbols, links, members/signatures as spans, mapper/inference,
     scratch, integer relation keys) into a checker arena, keeping `NodeId`/`SymbolId` for syntax and binder unchanged. This attacks
     the 58% bucket without touching emitter, LS, API node handles or the fingerprint tool.
  3. For the front end, take FE4 (parse directly into final identity ranges, priced at publication/adopt ≈ 4.1 G; the node-order
     audit found no dependency) plus the parse-time request collection, without changing `NodeData`.
- *Evidence.* M1 split at B0: semantic 30.8 G of the 53.1 G gap. The FE4 price is in the ledger. B-2 bounds the copies. PGO is in
  slice 8.
- *Cost.* ≈ 45–60 person-days. No `NodeData` migration (8,400 sites stay). Blast radius is checker/types/api only. Expected (derived):
  ≈ 108–115 G normal, ≈ 90–97 G PGO, peak ≈ 2,200–2,400 MiB.
- *What is lost.* Inline binder fields (memory only, ≈ −70 MiB) and the node layout change.

**A2 — Phase 0b de-risk before either plan (my recommended first step regardless).**
- *Mechanism.* Five throwaway builds, about one week:
  - (i) Bump global allocator, no free, on next.js/zod/VS Code.
  - (ii) Dense unchecked arrays for the five hottest links fields.
  - (iii) Parse into the final arena with inline binder fields and no publication, run only through parse + bind + fingerprint.
  - (iv) The `data()` view-enum dispatch on the 50 hottest match sites.
  - (v) The M1 ledger at #913 as B1.
- *Evidence.* The consult's ceiling experiment was planned (M3) and never run. Every forecast in this track landed at 20–50% of its
  ms-based estimate (ledger 計算の作法).
- *Cost.* 5–7 person-days, no freeze. The output is a priced component ledger that replaces §8.
