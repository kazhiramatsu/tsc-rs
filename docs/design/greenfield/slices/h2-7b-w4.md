## 3. Mechanisms ported

### 3.1 The integrator's harness / program items (implemented 2026-09-06 06:20-06:50 in `tsc-rs-w4-i` during the w3 gate; 10 of 10 rows exact through the frozen controls `crates/compiler/tests/integration/h2_7b_w4i_controls.rs`, replayed through BOTH the qualified loader with the recorded file-level `vfs_symlinks` and the runner's own `recorded-compiler-plan` route; the TS5055 pair through the `project-mount` route)
- **S2a — directory links in the suite VFS** (`crates/harness/src/upstream_suites/execution.rs`): the VFS builder published an alias only for a link whose target was an exact file; a `@link: dir -> dir` directive was silently skipped, so every symlinked package was invisible (TS2307, `any`, exit 2). Now a directory link publishes every descendant of its target under the link-relative suffix (byte-identical content + `realpath` override to the physical file), repeated to a fixpoint so links reached through other links expand too — upstream's vfs mounts the target directory node at the link path (`_tsc.js:41239-41246` accepts each aliased file; `:40047-40054` keeps original and real spellings).
- **S2b — the symlink cache** (`crates/program/src/symlinks.rs`, new; `prepared.rs` `ResolutionTable::modules()`; `crates/emitter/src/host.rs` `EmitHost::symlinked_{files,directories}` defaults; `crates/compiler/src/lib.rs` `PreparedEmitHost` computes the facts once; `crates/emitter/src/declarations/tracker.rs` the adapter forwards them): module-specifier generation's `symlinked_files()` / `symlinked_directories()` were the trait's empty defaults, so a file reached through a symlinked package was always named by a relative path. Ported `createSymlinkCache` (`_tsc.js:18331-18382`: `processResolution` records `(real, symlink)` per resolution with an `originalPath`) and `guessDirectorySymlink` (`:18383-18393`: the common tail below any `node_modules` / scoped directory) + `containsIgnoredPath`.
- **S2c — the runtime-dependency prelude** (`crates/program/src/loader.rs` `resolve_runtime_dependency_symlinks`; the prepared program carries `dependency_symlink_resolutions`): upstream's `getAllModulePathsWorker` (`_tsc.js:45717-45741`) resolves every `dependencies` / `peerDependencies` / `optionalDependencies` name of the importing file's package scope from `<package>/package.json` and feeds each resolution to the symlink cache — that is how `packageC` names `Foo` as `package-a` although it never imports it directly (proved with the real compiler on real symlinks: the trace shows "Resolving module 'package-a' from '.../packageC/package.json'"). The program runs it once at preparation (before the package table is collected, so the alias-spelled `package.json` files it reads serve the `exports` mapping later: `package-a/cls`), keeps only symlink-bearing resolutions, and exposes them to the cache; the only observable product — the cache — is identical to the lazy upstream order for these fixtures.
- **P1 — the project runner's config identity** (`crates/harness/src/upstream_suites/execution/project.rs`, the two emitting config arms): `.without_config_file_path()` dropped the parsed config's identity, so the emitter added the "Adding a tsconfig.json file will help…" hint to TS5055 (upstream chains it only when `!options.configFilePath`, `_tsc.js:125033-125040`). The adapter now keeps `configFilePath` but drops the config SOURCE FILE (upstream's project runner parses through `parseJsonConfigFileContent` with the file name and no source node), so option diagnostics such as TS5107 stay global exactly as frozen.
- Guards run at E1 on the merged tree: the program crate's unit tests (2 new `guess_directory_symlink` tests), the harness crate's tests, clippy/fmt, and the full bands (the VFS change touches every compiler-suite case with links; the symlink facts feed every declaration emit).
