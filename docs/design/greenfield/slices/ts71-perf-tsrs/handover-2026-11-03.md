### 2.2 step 2 で何をしたか（README 下書きの要約）

`TypeData` を `Copy` の 24 byte にし、`Type` を 40 byte・align 4 にした（`const` assert、`crates/types/src/ty.rs`）：

- union・intersection・reference・generic type・tuple target・template literal の型 list は、cache key 用に intern 済みだった
  `TypeListId`（`Box<[TypeId]>` の複製を消した）。intern した list 自体も list ごとの `Box` をやめ、checker に一つの平らな
  `Vec<TypeId>` + `(start, len)` の span にした。
- tuple target・template literal の payload、intrinsic の名前、bigint、string literal の文字列は tables 側の list への id。数値は
  `NumberBits`（f64 の bit 列 2 word、align 8 を避ける）。
- fresh/regular の対は header から freshable な variant（`Intrinsic`・`Literal`・`Enum`）と `Union` の payload に移した
  （`Type::fresh_type()` / `regular_type()` / `set_*`）。**object literal の regular type は record に置き場がない**：tsgo も
  record ではなく `cachedTypes[RegularObjectLiteral]` の side map なので（checker.go 28698）、`CheckerState.regular_object_literal_types:
  FxHashMap<TypeId, TypeId>` にした（`engine.rs get_regular_type_of_object_literal`）。test helper `relpin::mark_fresh_probe_source` は
  object に `fresh_type` を書くのをやめた（tsc/tsgo も書かない。freshness は `ObjectFlags::FRESH_LITERAL` だけ）。
- alias symbol + alias type arguments は `Option<AliasId>` 1 word（`TypeAlias` list）。header は `flags`・`object_flags`・`symbol`・
  `alias` の 16 byte。
- 読み方：`literal_value(ty) -> Option<LiteralValue<'_>>`（借用）、`LiteralValueOwned` は LS だけ、`tables.list(id) -> &[TypeId]`、
  `members_of` / `union_or_intersection_members`、`intrinsic_name`、`tuple_target`、`template_literal`、`alias_symbol` / `alias`。
- memory report の型の行は `capacity` でなく `len` で数える（claim した部屋の未使用部分は address 空間）。

memory report（VS Code、k1 対 h2、MiB）：型 256.0 → 98.2（2,575,538 × 40）、型所有の list と text 45.5 → 26.5、type list map
26.8 → 20.4、checker 合計（accounted）2,128.8 → 1,946.2（−183）。peak RSS 4,261 → 4,110。他の行は不変（§4 の数字の出典。名前は
238,107 個、text 4.9 MiB）。

**課題：step 2 は memory を −156 MB（VS Code）稼いだが、命令数は step 1 より +0.3〜+3.0% 戻した**（h2 比では −0.5〜−1.9% で
slice 全体としてはまだ正）。原因は未計測。code の形からの候補、効きそうな順：

1. **union / intersection / reference の member list の読み**：`Box<[TypeId]>` の直接 deref が `tables.list(id)`（`list_items` の
   `ListSpan` → bound check 付きの slice）になり、member 走査 1 回ごとに load + bound check が増えた。hot（`maybe_type_of_kind`、
   `get_reduced_type`、relation の union 分岐、`infer_from_types`）。対策：`list_items` を `StoreVec<TypeId>`（または store crate の
   unchecked slice API）にして `list()` を bound なしの 1 load にする；span を `(start, len)` のまま呼び出し側で index 走査。
2. **`TypeData` の値 copy**：`match self.type_of(id).data`（24 B の copy）が、書き換え前の `match &...data`（借用）より重い箇所が
   あるかもしれない（特に `let TypeData::X(..) = ... else` の let-else は copy してから比較）。`rewrite40.py` が書き換えた約 450 か所を
   `grep -n "type_of(.*)\.data\b"` で見て、hot な関数は `&` の借用に戻す。
3. **alias の間接参照**：`alias_symbol(ty)` が `aliases[alias_id]` の 1 段増（instantiation の cache key、relation、display）。
4. **fresh/regular が payload の match に**：`regular_type()` / `fresh_type()` / `is_fresh_literal_type` が `data` の tag 分岐に
   なった（`is_type_related_to` の入口で毎回）。header の 2 word から tag 分岐 + payload 読みへ。
5. literal / intrinsic / tuple target / template literal の id 経由の読み（`literal_value`、`intrinsic_name`、`tuple_target`）。

**進め方**：samply で i1 と k1 を同じ case（zod か vue：差が大きく短い）で取り、`fcmp.py` で関数別の self 差を見る（profile
の採取は利用者が `run-samply.sh` で）。または候補 1 を先に試す（`list()` の bound 除去は小さい変更）→ `serial.py` で k2。**命令数が
i1 と同等に戻らない場合**：memory −156 MB（−3.7%）と命令数 +0.3%（VS Code）のどちらを取るかは利用者判断（§8）。peak memory を
同格の目標にした 11-02 の指示に照らせば、+0.3% で −3.7% は取ってよい trade と読めるが、Next.js/vue の +3% は大きい。

## 3. 計測と検証の作法

### 3.1 負荷

local は 1 process が CPU 100% まで：`cargo -j 1`、conformance `--workers 1`、test `--test-threads=1`、重い job は一度に一つ、
`nice -n 20`。build・test・計測・conformance を同時に走らせない。背景 job は一つ。

### 3.2 計測

- `target/claude-tools/perf11/serial.py OUT.jsonl label=bin,label=bin case,case`：1 case ずつ `/usr/bin/time -l` で命令数
  （instructions retired）、CPU、RSS、peak footprint を出す。tsc-rs は `TSRS_WORKERS=1 TSRS_CHECKERS=1`、label が `tsgo`/`tsrs` で
  始まる binary は `--singleThreaded`。case = `vscode/stable`、`ts/noemit`、`next/noemit`、`zod/noemit`、`effect/noemit`、
  `hono/noemit`、`vue/noemit`、`playwright/noemit`（corpora は `~/dev/bench-corpora/`）。wall time は参考にしない（別の job が
  同じ machine を使う）。
- `diffout.py A B cases`：出力（診断 + exit code）の一致。slice ごとに 8 case で必ず一致させる。
- binary は `perf11/bin/tsc-rs-<label>` に残す：`g3` = #848、`h2` = slice 10 最終、`i1` = slice 11 step 1、`pgo1` = #848 の PGO、
  `tsrs-sym-nopgo` = tsrs の通常 build。**PGO は PGO と、通常は通常と比べる**（混ぜない）。同じ base から作った binary 同士を
  比べる（layout の noise を避ける）。
- memory：`TSRS_MEMORY_REPORT=1`（stderr に `[memory]` 行：syntax・binder・checker の構造別の byte）。peak は `serial.py` の foot
  （footprint）と rss の両方を報告する（`time -l` の footprint は lazily-freed な page も数える）。説明のつかない分（peak 4,160 対
  accounted 3,640）は check 途中の一時物・`Vec` の余り・hashbrown の load。
- profile：`run-samply.sh`（利用者が実行）、`cmp2.py --by self --min N`（tsc-rs と tsrs の関数別）、`drill.py rs 's:REGEX:depth:n'`
  （inline を展開した呼び出し元。REGEX に `::` は使えない：`.` で代用）、`disasm.py BIN SYMBOL`、`callers.py`（gzip の profile 用）。
  PGO の学習 profile の呼び出し回数：`llvm-profdata show --all-functions --counts`。
- PGO：`python3 scripts/pgo_build.py --jobs 1 DIR[:TSCONFIG] ...`（6 project、1 thread で学習 → `target/pgo/tsc-rs`）。CLI の
  `libc::_exit` は atexit の profile writer を飛ばすので、`LLVM_PROFILE_FILE` があるときだけ `std::process::exit`（main.rs）。

### 3.3 最終 byte の check（PR 本文に書く）

**2026-11-03 利用者の判断（slice 13 の battery 2 時間の内訳：test 70 分、conformance 15 分 × 2、release build 7 分）**：
hosted `ci` が同じ script・同じ ratchet で走らせる検査（fmt、clippy、workspace の test 4,999 本、1 checker の conformance、
suites）は local で繰り返さない。local は hosted がやらないものだけ：

```sh
nice -n 20 cargo test -j 1 -p <変えた crate> -- --test-threads=1        # focused test（syntax・binder なら数秒）
nice -n 20 cargo build -j 1 --release -p tsc-rs-cli                   # + conformance-ts71 / suites-ts71 の release binary
python3 scripts/syntax_fingerprint.py --compare <baseline> --out <new> # front end を変えたら。exit 0（差 0 行）が gate
python3 target/claude-tools/perf11/diffout.py <base> <new> <8 case>    # 8 project の出力一致
python3 target/claude-tools/perf11/serial.py <out.jsonl> ... <8 case>  # 1 thread の命令数と peak
nice -n 20 python3 scripts/conformance_ts71.py --workers 1 --checkers 4 --check  # checker を変えた slice だけ。
                                                                       # mismatch が packet 記録の既知 4 件だけなら OK
```

battery は 15〜30 分になる。fingerprint の baseline は `target/claude-tools/handover/perf-tsrs/syntax-baseline/main-39058c48c.tsv`
（conformance corpus 12,951 file + bench 8 project 58,644 file × 2 JSDoc mode = 143,190 行）。PR は early に開いて hosted を
local と重ねる。exit status はそのまま見る（`tail`/`grep` を挟まない）。`ratchets/ts71/` は最終 byte で `--update` したときだけ
変える。PR body には command、source identity（TypeScript 7.1.0-dev `aa814927`）、結果、残る bounded difference を書く。merge は
hosted `gates` pass 後に `gh pr merge --merge --delete-branch`（merge commit のみ）。merge 後、main に記録段落（PR、merge commit、
hosted run、local の数字）。

Rust の test は code として残す（conformance では見えない tsgo の挙動を pin する唯一の記録、2026-10-13 の方針）。書き直す
syntax / binder の test だけは選別する：古い表現（Box の payload、scanner の内部状態）に縛られた test は表現と一緒に捨て、公開
API（parse → kind / 位置 / 診断）で書かれた test は機械的に追従させ、書き直し後に新しい不変条件（tail の配置、speculation の
巻き戻し、relocation の mask）を pin する test を少数足す。

### 3.4 単体 test の置き方

変えた経路は tsgo の出力に対する単体 test で pin する（`crates/*/tests/unit/...`、`#[path]` で include）。conformance で見えない
差（suggestion、related info、LS だけの message）には Rust の regression test。並列 test で active な range を数える test は
`IdentityLease::watch` を使う（flaky 対策）。

### 3.5 allocator（未着手の実験）

mimalloc v3.3.2 を global allocator にしている（`libmimalloc-sys` 0.1.49 既定。tsrs は mimalloc-safe v3）。allocator 側の余り
（mimalloc の peak committed 約 3.1 GB 対 live 約 2.5 GB、store の region 約 1.25 GB）の上限は約 0.6 GB。実験の手順は、
`MIMALLOC_*` の環境変数（purge delay など。rebuild 不要）→ system allocator の参照 build（p42、`main.rs` の `global_allocator` を
外す。commit しない）→ 命令数と peak の差を見る。優先度は低い（record の縮小と確保の削減が先）。

## 4. 現状の data model（record ごとの形と大きさ）

各節の原文（英語、file:line 付き）は `target/claude-tools/handover/perf-tsrs/*-report.md`（§11）。数字は特記がなければ VS Code
`src` 1 thread。

### 4.1 store（`crates/store`、唯一の `unsafe` crate）

- 予約：`FIRST_REGION = 0x4000_0000_0000` から region 8 つ × 2^38 byte（1 region = 2^32 slot × 最大 64 byte）。record 型ごとに
  `StoreRecord::REGION`：0 `Node`、1 `NodeArrayRecord`、2 `NodeId`（node array の item）、3 `Symbol`、4 `NodeSlot<SymbolId>`、
  5 `NodeSlot<FlowId>`、6 `PackedNodeFlags`（4〜6 は binder の per-node 表、`crates/binder/src/declare.rs`）、7 `Type`。**8 つとも
  使用中**：新しい record 型（node の payload tail、symbol の tail、links）には `REGIONS` を増やす（address 空間は 47 bit まで
  使えるので 32 region = 2^43 byte でも足りる。tsrs は 32 GiB を 1 つ）。読みは `get<T>(position)` = 定数 base + position × size の
  1 load（`#[inline(always)]`、bound なし）。契約：全 0 の record が有効な値、range は lease の持ち主が一度だけ publish、読む側は
  live な document の identity だけを名指す（`Arc` で保証）。identity space（`crates/types/src/identity.rs`）：Node 0、NodeArray 1、
  Symbol 2、PrivateNameSerial 3、NodeArrayItem 4、Type 5。
- `StoreVec<T>`：heap の `Vec` として作り `publish(position)` で store に複製するか、`claim_room(position, room)` でその場に作る
  （型は後者）。`record(index)` は長さ以下の index を bound なしで読む。`Placement { Heap, Mapped (≥ 64 KiB は mmap), Claimed,
  Published }`。drop 時は 0 で埋める（≥ 1 MiB は kernel に返す）。
- identity：`IdentityDomain` / `IdentitySpace`（Node・Symbol・…・Type = 5）、`lease(space, len)`、`IdentityClaim`（publish した木は一度に
  一つの binder が bind する）。

### 4.2 Node（48 byte、`crates/syntax/src/nodes.rs:72-97`）

原文：`target/claude-tools/handover/perf-tsrs/node-report.md`。

- header 24 B：`kind: SyntaxKind`（u16、必要なのは 9 bit）、`literal_flags: u16`（multiLine 2 bit、文字列/regex の 2 bit、数値・
  template の flag。bit 15 は空き）、`flags: i32`（NodeFlags、31 bit 使用）、`pos`/`end: u32`、`parent: Option<NodeId>`、`js_doc:
  Option<NodeArrayId>`（JSDoc host だけが持つ。CLI の `ParseForTypeErrors` ではほぼ全部 `None` で 65.6 MiB）。
- `data: NodeData` 24 B、align 8：196 variant（`Token` + 195 payload）、tag u8 + 3 B padding、inline payload は最大 20 B（9 種）、
  **52 variant が `Box`**（JSDoc 30 + ArrowFunction・Constructor・FunctionDeclaration/Expression・Get/SetAccessor・Method
  Declaration/Signature・Parameter・PropertyDeclaration・StringLiteral・NumericLiteral・BigInt・RegExp・template 4 種・JsxText・
  MappedType・ShorthandPropertyAssignment・NotEmittedStatement）。**Box の heap は memory report に数えられていない**
  （StringLiteral だけで 750,361 × 24 B = 17 MiB）。
- VS Code 17,193,142 node = 787 MiB。上位 12 種（71%）：Identifier 5.95 M（payload 4 B、48 のうち 19 B 未使用）、
  PropertyAccessExpression 1.53 M（12 B）、CallExpression 0.99 M（16 B）、StringLiteral 0.75 M（Box）、PropertyAssignment 0.55 M
  （20 B）、ExpressionStatement 0.50 M（4 B）、TypeReference 0.40 M（8 B）、Block 0.35 M（4 B）、VariableDeclaration 0.31 M（16 B）、
  VariableDeclarationList 0.31 M（4 B）、BinaryExpression 0.30 M（12 B）、token 0.30 M（0 B）。上位 12 種だけで未使用 181 MiB。
  195 payload のうち 118 は 12 B 以下。
- 親は `finalize_tree` が 1 回の下り走査で付ける。parse 後に binder/checker が node record に書く field は **ない**（binder の bit は
  region 6 の 1 B/node overlay、`node.symbol`/`node.flowNode` は region 4/5、checker の links は `PagedTable`）。emit は arena の
  detached copy を変更する。
- node array：`NodeArrayRecord` 20 B（region 1）+ item store（region 2、`StoreVec<NodeId>`、#606）。VS Code 3,119,430 array
  （59.5 MiB）+ 5,407,345 item（20.6 MiB）。parser は list ごとに一時 `Vec<NodeId>` を作って `alloc_array` で複製する（空でない
  list 1 つに malloc/free 1 対、VS Code で最大 310 万対。tsrs は 1 本の `node_stack`）。
- **relocate（parse 後の複製）**：loader は module discovery 中に private id（base 0）で parse し、program 順が決まってから node・
  array・item の正確な個数を lease し（`lease_identities`）、全 record の id を書き換え（`apply_identity_relocation` → 生成 code
  `relocate_node_data` 196 arm、Box は pointer chase）、`publish` で store へ `copy_nonoverlapping`。record を 1 回読み書き + 1 回複製
  = VS Code で 787 + 60 + 21 MiB の往復（profile 97 sample）。symbol は既に予約 range にその場で作る（`claim_room`）前例がある。
- 失敗した speculation の node は tree に残る（`try_parse`/`look_ahead` は arena を巻き戻さない）。数は未計測。
- tsrs：header 24 B（`NodeHeaderWord` = parent 45 bit + kind 9 bit + tag 8 bit + 2 bit、flags、id、loc）+ 同じ allocation の tail
  （Identifier 32、PropertyAccess 40、Call 40 + rare tail 8、StringLiteral 40、MethodDeclaration 80）。→ §6.2。

### 4.3 Symbol（48 byte、`crates/binder/src/symbols.rs:29-53`）

原文：`target/claude-tools/handover/perf-tsrs/symbol-report.md`（file:line 付き）。

| field | 型 | byte |
|---|---|---:|

5,890,486（live 270 MiB。report の 384 MiB は capacity：`clamp(nodes×2, 4096, 2^22)` = 419 万 slot が 1 回倍増して 839 万 × 48）、

  symbol から member を引くのに 6 段の load（record → extras box → Arc → boxed map → positions → entries）。
- `SymbolArena::symbol(id)` = `&self.symbols[self.index(id)]`：`#[inline]` なし、`index()` の `assert!(id >= base)` + `StoreVec::deref`

### 4.5 名前と文字列

原文：`target/claude-tools/handover/perf-tsrs/strings-report.md`。

- `JsString`（`crates/diagnostics/src/js_string.rs`）= 24 B（`Storage` Inline 15 B / Heap `Vec<u8>`、`Option` も 24 B）、
  `JsStr<'a>` = 16 B（ptr, len）。符号化は canonical WTF-8（byte 等価 = UTF-16 等価、順序は `cmp_utf16`）。`as_js()` は tag の
  load + 分岐、`JsStr::as_str()` は毎回 O(n) の UTF-8 検証（`IdentifierData::text()` と `numeric_token_value` が毎回払う）、
  `clear()` は heap の `Vec` を保持する（一度 15 B を超えた `token_value` は heap のまま。以後の `save()` は malloc + memcpy、
  `restore()` は free）。
- 名前表（`crates/types/src/names.rs`）：`EscapedName(u32)` → `chunks[id/4096]`（`OnceLock<Box<[OnceLock<Name>]>>`）→ slot
  `OnceLock<Name>` 32 B → `Name { text: &'static JsString, scalar: Option<&'static str> }` 24 B → `Box::leak` した `JsString` 24 B →
  Inline/Heap。読みは 7〜8 load + 5 分岐、依存 3 段（cold なら cache miss 3〜4 回）。1 名あたり約 62〜68 B + 15 B 超の text。
  intern は thread-local の `Recent` cache（8,192 slot × 32 B = 256 KiB/thread）→ 64 shard の `Mutex<HashTable<u32>>`。**shard を
  hash の上位 6 bit で選んでいて、hashbrown の 7 bit tag と衝突**（shard 内の tag が 2 値しかなく、group の半分が偽一致。
  `(hash >> 32) % SHARDS` に直す）。VS Code の名前数は 238,107（text 4.9 MiB。report の "names" 行は text byte だけで、slot
  32 B + leaked `JsString` 24 B を足すと約 18 MiB）。
- `== "literal"` の比較：`EscapedName == "x"` は名前表の読み + 比較（checker 62 か所、全 crate で `default` 32・`this` 21・
  `export=` 15・`require` 12 …。hot：`resolve_name` の scope step ごとの `const`（`resolve.rs:297`）、`default`（433・476）、
  `arguments`（689・697）、symbol ごとの `this`（`exports.rs:944`）、declaration ごとの `require`/`exports`（`statements.rs:1385/1389`）、
  binder の `arguments`/`eval`（`bind.rs:1924`）、`push`/`unshift`（`node_util.rs:3134`）、tuple の `length`（`structural.rs:2630`））。
  `known_name!` 16 か所（`OnceLock` 読み）。`InternalSymbolName` の `&'static str` で表を引く 34 か所と `EscapedName::internal` 約
  40 か所と `get_global_*("…")` 41 か所は**毎回 intern**する。
- scanner（`crates/syntax/src/scanner.rs`）：`token_value: JsString` に識別子ごとに複製（`scan_identifier_parts` は ASCII run を
  `push_str`、1.1 億回）、`finish_identifier_token` は source slice を再構成して `memcmp` で escape の有無を見てから keyword を
  文字列 `match`、数値は `to_owned()` → `.into()` で 2 回複製（16 進は `format!`）、`ScannerState` 72 B の clone が `save()`
  （`look_ahead` 56 か所 + `try_parse` 13 か所 + jsdoc 8 か所。型 member・class member・modifier・keyword 型ごとに 1 回。識別子
  node 600 万に対し識別子 scan 1.1 億回の理由の一つ）。
- parser：識別子は `EscapedName::escape(token_value())` で intern（`current_token_name`）。string literal・template は `to_owned()`
  で `Box<StringLiteralData { text: JsString }>`（24 B の box + heap）、numeric/bigint/regex/JsxText は `as_str()`（UTF-8 検証）
  → `String`。jsdoc は `String` 経由。
- string literal 型の表（`crates/types/src/tables.rs`）：同じ text を **3 回**保持（UTF-16 key の map、UTF-8 `Vec<u8>` key の map、
  `literal_texts` の UTF-16）。新規 1 件で確保 3 回。VS Code で 2 map 56 MiB（N ≈ 40 万）。`property_name_from_type` などは
  literal 型の text を `TemplateText::to_js_string()`（1 code unit ずつ push）で再符号化してから毎回 intern する（profile の
  `append_code_point` 15）。
- tsrs：intern なし、`&'static str`（source slice か arena）、`PackedStr` 8 B、scanner の `token_value: &'static str` は Go が
  substring を返す場面では source の slice。identifier の text は node に持たず `source[end − len .. end]`。

### 4.6 links・per-node 表・routing

原文：`target/claude-tools/handover/perf-tsrs/links-routing-report.md`（数字は slice 1 時点の VS Code memory report
`perf11/phase-a6.log`。links と binder の行は layout の変更に影響されない）。

- `PagedTable<K, T>`（`crates/checker/src/links.rs:1284-1293`）：`index: Vec<Option<Box<[u32; 256]>>>`（256 id ごとの page に
  slot+1）、`far: FxHashMap`（id ≥ 2^26）、`chunks: Vec<Vec<T>>`（256 record の chunk、動かない）。`get` の hit path は約 9 load
  （依存 4 段：page pointer → slot → chunk pointer → field）+ 分岐 6 + bound check 3、約 25 命令、far path の hash 探索が本体に
  inline されているので本体が大きく inline されない（tsrs は hash path を `#[cold] #[inline(never)]`）。`with_capacity_hint` は
  引数を無視している。
- record（全 field 4 B、assert あり）：`NodeLinks` 16 B（resolved_type / resolved_signature / resolved_symbol の `IdSlot` +
  check_flags）、`SymbolLinks` 28 B（declared_type、type_of_symbol、check_flags、is_referenced、target、mapper、name_type）、
  `TypeLinks` 36 B（resolved_members、type_parameter_constraint、resolved_base_constraint、type_parameter_default、
  instantiated_target/mapper、type_parameter_target/mapper、deferred_node）。`IdSlot` は 4 B（0 = Vacant、MAX = Resolving）、
  `LinkSlot<Id>` は 8 B（cold 表 21 個がまだ `LinkSlot` を使う）。cold 表は field ごとの `FxHashMap`（node 6.3 / symbol 28.5 /
  type 11.0 MiB）。
- 占有（VS Code 1 checker）：node links 5,591,818 record = 150.4 MiB（record 85 + page 65：256 id page の 97% が触られる = 実質
  dense）、symbol links 7,113,591 = 253.6 MiB（record 190 + page 63。persistent id は file の node 数ぶん lease されるので約 13% の
  密度、transient は dense）、type links 1,479,111 = 60.9 MiB。**`SymbolLinks` の `check_flags`・`target`・`mapper`・`name_type` は
  transient symbol にしか書かれない**（711 万 record のうち約 589 万が transient）。
- id 空間：type は checker ごとに dense（2^26 の lease）、transient symbol は checker ごとに bit 31 から dense、node と persistent
  symbol は process 全体で共有（複数 checker・複数 Program）。
- binder の per-node 表は既に program 全体で store の position を key にしている（routing なし）：`node.symbol` region 4（4 B、
  65.6 MiB、占有約 13〜15%）、`node.flowNode` region 5（4 B、65.6 MiB、占有約 45〜50%）、`PackedNodeFlags` region 6（1 B、16.4 MiB、
  **8 bit 中 6 使用、2 bit 空き**）。`locals` は file ごとの `FxHashMap<NodeId, SymbolTable>`（359,372 entry、48 MiB）。
- `FlowNode` 32 B（flags 4 + `FlowPayload` 24（`Label { antecedents: Vec }` など）+ antecedent 4）、`FlowId` は file ごとの index。
  VS Code 2,389,109 個 = 105 MiB の報告だが live は 73 MiB（**`into_bind_data` が shrink しないので 32 MiB は `Vec` の余り**）。
  checker は label の antecedent を訪問ごとに `Vec` に clone（`flow_label_antecedents`、8 か所）。tsrs は 16 B。
- routing（`try_file_index_of_node`、`program.rs:1114-1135`）：`DenseOwners` = 256 id の page 表 → owner 区間の短い走査、約 12 load
  + 分岐 6〜8、約 30 命令、out-of-line。checker の `source_of_node` 329 + `file_index_of_node` 110 か所の内訳：JS file だけの data
  （hosted JSDoc、"is JS file"）約 102 + `is_in_js_file` 98 呼び出し元 + `hosted_jsdoc` 13 → **node の `JAVA_SCRIPT_FILE` flag で
  答えられる**（parser が JS/JSX file の全 node に立てる。tsc の `isInJSFile` そのもの）；tree の読みだけ約 64（`&impl
  NodeLookup` で済む）；source text と位置 約 66（診断・表示、cold）；file の identity 約 67（cold）；per-file の binder 表と flow
  約 10 + helper（`locals_of` 21、flow arena 9、`node_end_flow` 等 4、`node_local_symbol` 3、`next_container` 2、CJS indicator
  29）；Program/module の事実 約 30（memo 済み）；emit・表示 約 46（cold）。
- `resolve_name` は祖先ごとに `kind_of` → SourceFile なら CJS 判定（routing）→ `locals_of`（routing + hash probe）を払う。祖先の
  75〜85% は locals を持たない。

### 6.0 全体の順序（提案。利用者が決める）

見込みは VS Code 1 thread（命令数 h2 172.8 G、peak 4,160 MB。tsrs 通常 build 86 G、2,021 MB）。命令数の見込みは code の形からの

### 6.1 文字列（原文 `strings-report.md`）

**証拠**：§4.5。memmove の `to_owned` 30 + `push_str` 17 + `append_code_point` 15 + `save` 8 + `parse_string_literal` 7 sample、
scanner 5%、`as_js` 5,200 万回、`JsString == str` 3,000 万回、string literal 表 56 MiB。

**0. すぐ直せるもの**：`names.rs:163` の shard 選択を `(hash >> 32) % SHARDS` に（hashbrown の tag と衝突している）；
`numeric_token_value` の毎回の UTF-8 検証；jsdoc の `token_value()` が常に `String` を返す（`jsdoc.rs:74-86`）；`Recent` hit の counter。

**1. token value を source slice に**（−1〜−2%、parse の確保を消す）：

```rust
#[derive(Clone, Copy)]
pub(crate) struct ScannerState {     // Copy、約 40 B（今は JsString の clone 込みで 72 B）
    end: u32, pos: u32, full_start_pos: u32, token_start: u32,
    value_start: u32, value_end: u32,  // `text` の範囲。COOKED のときは `cooked` の範囲
    token_flags: TokenFlags,           // 新 bit: COOKED
    error_len: u32, token: SyntaxKind,
}
// Scanner は `cooked: JsString` を scratch として持つ。save() は COOKED のときだけ cooked を clone して返す。
```

- `token_value() -> JsStr<'_>` は `&self.text[s..e]`（escape なし）か `cooked`。`token_value_source() -> Option<&'text str>` を足し、
  呼び出し側が `next_token()` をまたいで slice を持てるようにする。数値・regex・JSX・JSDoc 用に `token_value_str()`（文法上
  scalar text なので UTF-8 検証なし）。
- cooked が要る token：`\u` escape の識別子、`\` escape か行継続のある string literal、escape か CR のある template、正規形でない
  数値（separator、先頭 0、小数、指数、16 進、15 桁超）、separator や大文字 16 進の bigint。JSX 属性文字列・regex・JsxText・JSDoc
  comment text は常に slice。全書き込み箇所の表は原文 §4.3。
- `scan_identifier_parts` は `pos` を進めるだけ。最初の `\u` で `text[value_start..escape]` を `cooked` に複製して COOKED。
  `finish_identifier_token` は `keyword_kind(&text[value_start..pos])` を直接（`memcmp` なし）。
- **共有の append-only `JsString` を cooked の arena にしない**：`push_js` が末尾の lead surrogate と次の trail を結合するので、
  2 token を続けて書くと両方壊れる。
- LS の scanner（astnav、formatting、`scan_byte_tokens`）は `token_value` を読まないのに push を払っている → 同時に速くなる。

**2. string literal 型の表を id key に**（−0.3〜−1%、約 −50 MiB + 型側 N × (16 + 2L)）：`FxHashMap<JsText(u32), TypeId>`（bucket
9 B）と `LiteralData::String(JsText)`、`literal_texts` を消す。text は名前と同じ共有 arena に 1 回だけ。WTF-8 の byte 等価 = UTF-16
等価なので map の identity は同じ。`property_name_from_type` / `try_get_name_from_type` は flag test に（`__` で始まる text だけ
`"_" + text` を intern、他は同じ id）。`get_string_literal_type(unescape(name))` は `___` で始まらなければ name の id をそのまま。
`LiteralValue::String` の読み手 41 か所は `JsStr<'static>` の view（`code_units`・`cmp_utf16`・`as_str`・byte 長）。順序は
`JsStr::cmp_utf16`（今と同じ）。

**3. 名前表を平らに**（−0.3〜−0.6%、−10〜−20 MB、process 全体）：`unsafe` が要るので `crates/store` の中に置く（`types` は
`forbid(unsafe_code)`）。`REGIONS` を 10 に：record region（`NameRecord { start: u32, len_flags: u32 }` 8 B、定数 base + id × 8、
cache line に 8 個）+ text region（append-only の byte arena、`fetch_add` の cursor で range を取り、byte を書き、record を書き、
その後 shard の mutex の下で id を公開）。`len_flags` の上位 6 bit：`NOT_SCALAR`（lone surrogate あり）、`DUNDER`（`__`）、
`TRIPLE_UNDERSCORE`（`___`）、`LATE_BOUND`（`\u{FFFD}@`）、`NUMERIC_NAME`（今は毎回 `String` を parse/format する
`is_numeric_literal_name`）、`PRIVATE`（`#`）。読み：`as_js()` = 8 B load + mask + add、分岐なし；`as_str()` = + flag test、
UTF-8 検証なし（intern 時に検証済み。`from_utf8_unchecked` は store crate の中）。`JsStr` に intern 済み byte 用の信頼 constructor
（sealed token）が要る（byte からの constructor が今はない）。atomic load は不要：id は shard mutex・document の `Arc`・定数で
しか読み手に届かない（`store::get` と同じ契約）。`'static` を要する読み手（`identifier_text_of` 108 か所、`IdentifierData::text()`
97 か所、`ObservableField::String(&'a str)`）は process 寿命の固定 address arena なら今のまま。

**4. known name の定数**（−0.1〜−0.3%）：id 0..K を静的表から seed（id 0 = `""`、`InternalSymbolName` 20 個、§4.5 の literal
30 個ほど、任意で keyword 全部）。`pub const DEFAULT: EscapedName = EscapedName(n)`。`known_name!("x")` は定数（表にない literal は
compile error）、`EscapedName::default()` も定数。T 型の比較（識別子 text と `&str`）を escaped id の比較に書き換える
（`escaped_text_of(n) == Some(names::THIS)`）。escape 規則：escaped name と比べる定数は escaped 形で持つ（`__proto__` →
`___proto__`）；internal name は verbatim（user の `__call` は `___call` になるので衝突しない）。**定数 id を順序に使わない**。
`record(id)` は `if id < K { KNOWN[id] } else { region }`（region 予約前にも定数を読める）。

**5. literal の payload**：`StringLiteralData.text` → `JsText(u32)` inline（24 B の box + heap が消え、file 間で重複排除）、template
の cooked text も id、`raw_text` は source range から導く、numeric/bigint は `Box<str>` か id、regex/JsxText は node の range から、
JSDoc text は `Box<str>`。emitter は parse した literal を source の byte で印字するので cooked text は合成 node だけ。

**6. 薄い不変 `JsString`**（24 → 16 B、残る用途は cold）：最後。

**出力 identity の risk**：名前の順序は text の JS 順（`cmp_utf16`。`type_order.rs:211-234, 268`）で id で並べない；`EscapedName: Ord`
は byte 順のまま（`BTreeSet` が 1 か所）；known name の seed で全 id がずれる → `EscapedName` を key にする hash 容器 23 個が
lookup だけか確認（`SymbolTable` は挿入順）、8 case の byte 一致が gate；lone surrogate の診断は U+FFFD（`NOT_SCALAR` =
`from_utf8(bytes).is_err()`）；`escapeLeadingUnderscores`（raw の `JsText` と escaped name は `__` で始まる text で違う）；cooked
escape は canonical byte を作る（`push_js` の結合）；scanner の端 case（数値の正規化 `scanner.rs:2599-2630`、bigint 16 進の小文字化、
template の CR 正規化と tagged template の raw、escape で綴った keyword は cooked text から検出して TS1260、`re_scan_*` は位置だけ
戻す）；**LSP の長寿命 process では string literal の text を process 全体の表に intern すると edit ごとに表が育つ**（今の
append-only の根拠は識別子だけ。emitter の合成 literal も intern する）→ §8。

### 6.2 Node 48 → 32 byte、relocate の廃止、parser の list stack（原文 `node-report.md`）

**証拠**：§4.2。record 787 MiB（上位 12 種だけで未使用 181 MiB、`js_doc` 65.6 MiB、Box の heap は未集計）、relocate 97 sample、
list ごとの malloc/free 310 万対。tsrs の node は 24 B header + tail。

**形を決める制約**：`store::get` は region ごとに固定長 record を前提にする（可変長の tail を header の直後に置くと dense な
index で届かない）。tsc-rs の `NodeId` は handle であると同時に dense な index で、binder の per-node 表（148 MiB）・NodeLinks
の page・`DenseOwners`・copier の mark・parser の reachability mask が依存する。tsrs の inline tail を真似ると id が疎になり、
per-node 表が約 4 倍に広がる（代案の「header に tsrs の `id` を足す」は side table の読みごとに依存 load が 1 つ増える）。種類
ごとの region も無理（8 region 全部使用中、約 77 種に region と lease space が要る）。→ **固定 32 B の record（region 0）+ 1 本の
tail word store（新 region 8、`array_items` と同じ形）**。

```rust
#[derive(Clone, Copy, Debug, PartialEq)]
pub struct Node {                 // 32 B、align 4、全 0 が有効、Copy
    pub kind: SyntaxKind,         // 2（`.kind` の読み約 1,380 か所はそのまま）
    pub literal_flags: u16,       // 2（bit 15 = HAS_TAIL。`TOKEN_FLAG_BITS` の mask で 1 bit 追加で空く）
    pub flags: i32,               // 4 parse 時の NodeFlags（binder の overlay は今のまま）
    pub pos: u32, pub end: u32,   // 8
    pub parent: Option<NodeId>,   // 4
    words: [u32; 3],              // 12 payload：inline の field、または [tail, hot, hot]
}
```

- **配置は種類ごとに生成**（`nodes.schema.json` + hot field の順序）：payload が 3 word 以下なら inline（118/195 種 + Token）。
  それ以上の種類は、hot 3 個以外が全部 `None` なら hot 3 個を inline、そうでなければ `HAS_TAIL` を立てて `words = [tail_offset,
  hot0, hot1]`、残りは tail store。これは tsrs の rare tail 規則（`?.` は call の 0.1%、type argument は 0.5%）で、
  CallExpression・PropertyAssignment・VariableDeclaration はほぼ tail を持たない。Box の 52 種は `Copy` の struct になり同じ規則で
  配置。`js_doc` は header から出す（payload 2 word 以下の種類は空き word、他は tail。`HAS_JS_DOC` bit）。literal の text は
  §6.1 の id（`JsString` は全 0 が無効なので store に置けない）。
- **読み書き**：`NodeData` は名前と variant 名を保ったまま**値の `Copy` view**（最大約 40 B の一時物。`&XData` の view は safe
  code では作れない）。同じ型を `alloc_node` の builder に使う。`NodeLookup::data(&self, node) -> NodeData`、`tail()`、`text()`、
  `js_doc()`。`match self.data_of(n) { NodeData::X(d) => d.field }` はそのまま compile（`d` が値になる）。壊れるのは `*field`、
  `&XData` を期待する引数、`&**box`、`String` の move out（compile error に導かれて直せる）。view の `.clone()` は無料になる
  （checker 135・emitter 231・ls 18 か所。今は Box 種類が clone ごとに確保）。payload の変更は `arena.set_data(id, NodeData)`
  （parser 2 か所、emitter の `factory.rs:719, 862, 5485` と `with_data`、API decoder）。
- **生成 code**：`nodes.rs`（4,231 行）、`for_each_child.rs`（6,090）、`relocate.rs`（6,338）、`observable_fields.rs`（1,796）の
  generator `crates/xtask/src/node_codegen.rs` は `b27eb13bb` で削除され、以後手で編集されている（slice 4、#606）。**`b27eb13bb^`
  から generator を復元して今の file を再現できるようにしてから、layout の metadata（Box、hot 順）を足す**。LS/API の encoder は
  `scripts/generate_api_encoder.py`。
- **機械的な部分**：`.data` の field 読みを accessor に（`node(..).data` syntax 52・binder 221・checker 56・emitter 800・ls 334・
  program 26・api 3、変数経由 約 290）、単一種類の test を `as_x()` に（checker の let-else 415・if-let 74・`matches!` 58）、
  `Box::new` の削除と deref の修正（227 行）。**機械的でない部分**：tail/text store と region・lease space、tail の relocate と
  publish、`SubtreeCopier`（`arena.rs:170-286`）、構造等価（`arena.rs:44-60`、`incremental.rs:305-326`）、memory accounting、emitter の
  変更経路、hot path の decode 費用（`data_of` 1,570 か所。`kind` を先に見る）。
- **relocate の廃止**：parse 前に node・array・item・tail の room を lease し、`StoreVec::claim_room` で base = lease 先頭の arena を
  作る → parse 後に lease を使用数へ縮める（`IdentityLease` に shrink がないので allocator の新 API。bump 末尾なら
  `trim_free_tail` で返り、program 順の逐次 parse は今と同じ id になる）→ `validate_lease` の exact-length check を緩めて
  `publish`（複製なし）→ 溢れたら今の relocate に fallback（binder の overflow と同じ）。決定性：calling-thread の fresh parse は
  program 順で問題なし；loader が module discovery 中に parse する tree は、discovery 順で決定的に lease するか、program 順でない
  id を受け入れる（routing は区間を start で sort 済み、共有 document は既に program 順を破る、file 内の id 順は保たれる
  （emitter の `BTreeMap<NodeId, …>`）。残る risk は file をまたぐ生の NodeId 比較で、監査が要る）→ §8。text 長からの見積もり
  （VS Code 平均 node 8.3 B / array 45.8 / item 26.4、予約比 5 / 40 / 20）には margin と fallback が要る。
- **parser の list stack**（tsrs R14、parse −6%、全体 −1% 前後）：`parse_list`・`parse_delimited_list_worker`・`parse_modifiers`・
  union/intersection の `vec![t]` などが list ごとに `Vec<NodeId>` を作る → 1 本の `node_stack` に積み、`alloc_array` で 1 回だけ
  item store に複製。
- その他：modifier の flag を毎回 list を歩いて再計算している（`node_util.rs:700-744`）→ `NodeArrayRecord` の 2 B padding に u16
  の syntactic modifier flags を cache（tsgo/tsrs の `ModifierList` と同じ）；失敗した speculation の node 数を計測する（tsrs は
  rollback を recycle）。
- **見込み**：record 787 → 525 MiB（−262、exact）、tail +5〜45 MiB（rare tail 規則なら top 12 はほぼ 0）、合計 −220〜−255 MiB +
  未集計の Box heap。24 B record + inline 1 word の variant は 485〜505 MiB だが PropertyAccess/Call/Binary/TypeReference の読みに
  依存 load が 1 つ増えるので採らない。先に memory report を全種類印字（`take(12)`、`checker/lib.rs:3743`）して Box の byte を
  `add_memory_usage` に足す。

### 6.3 Symbol 48 → 32 byte（+ transient の unchecked read、表の軽量化）

**証拠**：§4.3。record 104 + 270 MiB、clone/instantiate ごとの `Declarations` 再確保、`symbol()` の 2 重 bound check（2.1 億回）、
表の 6 段 load。tsrs は 32 B。

**目標の形（Option B、変更が最少。32 B、align 8）**：

```rust
pub struct Symbol {
    pub flags: SymbolFlags,                // 4: bit 28 = ConstEnumOnlyModule, bit 29 = ReplaceableByMethod（tsgo と同じ bit）
    pub escaped_name: EscapedName,         // 4
    pub value_declaration: Option<NodeId>, // 4
    pub parent: Option<SymbolId>,          // 4
    pub declarations: DeclarationSpan,     // 8: { items: u32 (store の position), len: u32 }、Copy、Deref<[NodeId]>
    extras: Option<Box<SymbolExtras>>,     // 8: members, exports, global_exports, export_symbol, Option<Box<IndexMap>>
}
```

- `DeclarationSpan` は node array の item と同じ region 2（`NodeId`）を `tsc_store::slice` で読む。空の span は store に触らず
  `&[]`。全 0 の record は有効。field 名を保ち `Deref` を付ければ `.first()`・`.iter()`・`.len()`・`for &d in &x.declarations`
  （checker 約 300 か所）はそのまま。`.clone()` は span の copy（instantiate の確保が消える）。書き換えるのは追記する約 27 か所。
  `PartialEq` は中身で比べる（今の `Declarations` と同じ）。
- binder の pool：bind 中は worker-local の `SmallList` を `SymbolArena::declarations(id)` で読み（binder 17 か所）、publish 時に
  symbol の lease と一緒に取る NodeArrayItem の lease へ書く（`lease_batch`、`crates/checker/src/lib.rs:6381-6385`、上限 = node 数。
  overflow 経路 `declare.rs:567-611` にも lease）。checker の transient pool は `TypeTables::new` と同じ chunk 単位の lease
  （span は chunk をまたがない：claim した room を超えると address が変わる）。
- `SymbolExtras` は `IndexMap` を box にし bool を flag に移して 104 → 約 40 B。`export_symbol` は extras へ（export_symbol だけを
  持つ symbol が 10〜20 万個あり +4〜8 MiB。全部 u32 の Option C（`tail: Option<TailId>` を新 region に）なら避けられるが
  relocation の仕事が増える）。
- flag bit：`is_replaceable_by_method` は bool → bit 29（set `declare.rs:732-737`、read `declare.rs:741-759`、`annotate.rs` 3 か所、
  api）。`const_enum_only_module` は binder だけが 3 値を要る（latch `containers.rs:776-784`）：tsgo と同じく bit 28 + binder-local
  の `not_const_enum_only_modules` set。出力を変えないために `create_symbol(source_flags)`（`instantiate.rs:715-733`、
  `structural.rs:6565-6567`）と merge の OR（`merge.rs:291`）で bit 28/29 を mask し、clone 経路 2 か所では bit 28 を明示的に立てる
  （今はどちらも複製されない）。
- transient は同じ struct。読みは `StoreVec::record(index − BIT)` の `#[inline(always)]`（`type_of` と同じ形）。**transient の store
  上の位置は変えない**：絶対 id が観測される（`type_order.rs:220-223` の sort tie-break、`annotate.rs:1294-1297` の `__@name@{index}`、
  links の dense index）。
- `MAX_RESERVED_TRANSIENT_SYMBOLS`（`crates/checker/src/lib.rs:3631`）を上げて VS Code で arena が倍増しないようにする（report の
  384 MiB は capacity、live は 270）。

**手順（各段で出力一致）**：(1) transient の unchecked read + 予約上限 → (2) accessor `export_symbol()`・
`is_const_enum_only_module()`・`is_replaceable_by_method()` → (3) flag bit と latch と mask → (4) `export_symbol` を extras へ、
`IndexMap` を box に → (5) `DeclarationSpan`、size assert 32、memory accounting（`symbols.rs:253-276`）と古い「88 bytes」comment
（`symbols.rs:306`）の修正。検証：conformance、suites、8 case の出力一致、`Symbols` の統計が不変（README.md:341）。

**表（任意）**：`SymbolMap` に `MemberTable` と同じ ≤ 8 entry の線形 mode（positions は index だけなので順序に影響なし。binder 表
85 MiB のうち −15〜−25 MiB）、`Arc<SymbolTable>` を 1 allocation に（−5 MiB、load 1 段減）、`ABSENT` 表の `Arc::clone` の
refcount 競合を避ける（`annotate.rs:4682,4722,4726`）。tsrs が却下した「binder 表の凍結」（−9 MB で +0.4〜2.5%）はやらない。

**後の選択肢**：transient の `SymbolLinks`（28 B）を transient record に inline（60〜64 B、index page −30〜−45 MiB、
`PagedTable::get` を transient で省く。speculation の journal `links.rs:1386-1459` を inline record に広げる必要）。tsrs の
「instantiated symbol は header 16 B だけで data を共有」（−90 MiB 見込み）は copy-on-write が要る。

**見込み（VS Code 1 checker、live）**：binder record −35 MiB（+ pool 9.5）、extras −10〜−14、transient record −90（capacity 行は
−128）、合計 −120〜−130 MiB（peak の約 3%）。命令数は `symbol()` の bound check 2 つ分と declarations の clone 分。

**不変条件**：全 0 の record が有効・64 B 以下。publish 後の binder symbol は不変。transient の span が persistent pool を指しうる
ので document は checker より長生き（store の契約どおり）。clone した arena は pool の lease を共有（元が clone より長生き）。
declaration list をその場で編集する code はない（LS の `retain` は local copy、`crates/ls/src/definition.rs:312-323`）。

### 6.4 複製と確保、checker の record（原文 `checker-allocations-report.md`）

**訂正**：Signature は 136 B（`state.rs:143` の assert）で、243 B は memory 行（capacity 2^20 × 136 = 136 MiB + heap）÷ 個数

`capacity` で数えているものが多く、record の縮小の効果は live で見積もること**（型の行は slice 11 で `len` にした）。

### 6.5 links と routing（原文 `links-routing-report.md`）

**証拠**：§4.6。`PagedTable::get` 2.3% + routing 1.2〜1.8% の sample、2 億 4,300 万回。まず census を instantiation ごとに分けて
「1.48 億 = symbol、0.95 億 = type」の仮定を確認する。

1. **`SymbolLinks` を 2 つの population に分ける**（−62〜−69 MiB、−1.0〜−1.4%）：transient は `ProgramBinder.transient` と平行な
   dense・zero-init の予約表（28 B、`id.index() − TRANSIENT_SYMBOL_BIT`、index なし、`create_symbol` で伸ばす）、persistent は
   12 B（`type_of_symbol`、`declared_type`、`is_referenced`）の 2 段表。`get_check_flags` は persistent id に lookup なしで 0
   （tsc の意味）。`read_symbol` 64 か所、`name_type` の直読 17、setter 約 110、journal（`links.rs:1756-1803, 2459-2486`）。
   出力 risk なし（memo。走査しない）。debug assert：transient 専用 field は transient id にしか書かれない。
2. **routing を node flag と `NodeLookup` で消す**（−0.4〜−0.7%、約 250 か所、機械的）：`is_in_js_file`（98）は node の
   `JAVA_SCRIPT_FILE` flag、`hosted_jsdoc`（13 + wrapper）は flag が無ければ静的な空表、`get_name_of_declaration`/
   `has_dynamic_name`（38 + 33）は tag 自身の flag を見て `&impl NodeLookup` に、modifier flag 関数（15 + 19、relation path 含む）
   も node 自身の flag、`is_import_call` と仲間（19）・`body_of`・`get_assignment_declaration_kind`・`.arena` の呼び出し元（30）は
   `&Published`。debug assert：publish 時に root の flag = `is_source_file_js()`。「JSDoc あり」は全 10 表の filter にならない
   （question_tokens は parameter、cast は operand、… を key にする）。
3. **flow**：(a) `into_bind_data` で flow arena を `shrink_to_fit`（−32 MiB、自明）；(b) 16 B の `FlowNode`（flags、node、
   antecedent、link）+ document ごとの antecedent/switch/reduce pool（−37 MiB）；(c) flow に global な position（新 `IdentitySpace::
   Flow`、新 region、全 0 有効の 16 B record）：query ごと・statement ごとの routing、`(usize, FlowId)` の cache key、label の
   `to_vec` が消える（−0.2〜−0.5%）。`node_flow` と flow node 内の id は publish 時に document の base で relocate（O(nodes) の並列
   pass）か、lease を密に見積もって overflow 経路。
4. **dense な `TypeLinks`**（−0.5〜−0.8%、memory ±0）：hot 24 B（`resolved_members`、`type_parameter_constraint`、
   `resolved_base_constraint`、`instantiated_target`、`instantiated_mapper`、`deferred_node`）を checker の type lease と同じ位置に
   zero-init で置く（新 region か checker 所有の mapping）。`type_parameter_target/mapper/default`（読み 2〜4 か所）は sparse map。
   Windows では `claim_room` が room 全体を commit するので room は program から見積もる。
5. **`resolve_name` の locals**（−0.4〜−0.8%、+9 MB/snapshot）：`PackedNodeFlags` の空き 2 bit に `HAS_LOCALS`（`into_bind_data`
   で `locals.keys()` から導く = 構成上 exact）と root の `EXTERNAL_OR_CJS_MODULE`、snapshot ごとの `FxHashMap<NodeId, &'a
   SymbolTable>`（約 36 万 entry。`ScopeTable::Borrowed` が既に `'a` を貸す）。dense な 4 B/node の表は +65.6 MiB なので作らない。
6. **`NodeLinks`（と persistent symbol）の 2 段表**（±0 MiB、−0.2〜−0.4%）：`top: Vec<u32>`（256 id ごとの page 番号、page 0 は
   共有の全 0 page）→ `pages: [[u32; 256]]` → `records`（slot 0 = default record）。`get(id) = &records[pages[top[id>>8]][id&255]]`
   = 依存 3 load、分岐なし、far path なし。当面の応急処置：`far` path を `#[cold] #[inline(never)]` にして `get` を inline させる。
   node id は全 checker・全 Program で共有なので、checker ごとの dense 表（+112 MiB、LSP で 16 KiB page 粒度）は不可。
7. 小物：`DenseOwners::lookup_index` が `owner.file` を直接返す；`set_node_resolved_symbol` が `sanctioned_rewrite` を計算して捨てて
   いる（`links.rs:3893-3916`）；cold 表 21 個の `LinkSlot<Id>` を `IdSlot` に；`generic_object_flags`（`FxHashMap<TypeId,
   ObjectFlags>`）を type の `IS_GENERIC_*` object flag bit に（tsc と同じ）；write-only の bind map（`node_flow_when_true/false`、
   `possibly_exhaustive`）を落とす；`with_capacity_hint` を実装するか消す；`locals` の `node_count/32` 事前 size を見直す。

**LSP**：node の position は document ごとの lease で、drop 時に scrub され、再利用される → document ごとの表は構成上 drop
できる；snapshot/checker ごとの position key 表は snapshot が document の `Arc` を持つので安全；**process 全体の `NodeId` key の
cache は作らない**（position が再利用される）；外部 handle（API、emit resolver）は fallible な router で検証し続ける。

**合計（1〜6）**：live −130 MiB、−3〜−5%。

| arena | 固定 address の store（record ≤ 64 B、region 8）+ heap の `Vec`/`Box` | 32 GiB の 1 予約、thread ごとの bump arena（leak）、free list による recycle、region（LSP/emit） | §6.6 |

tsrs が計って却った案（やらない）：atomic な base（+25%）、tag の checked `match`（+4.7%）、`declarations[0]` の bound check

pre-fault した arena（RSS +16〜36%）。原文 §9。

## 8. 利用者の判断が要る項目

1. **「同じ出力、違う counter」の memo**：tsrs の inference-walk memo（R10、VS Code −7.15%）、union front cache（R30）、indexed-access
   memo は fast mode 専用（Types/Instantiations の counter は同じで、診断も同じと主張）。tsgo parity の規則の下で採るか。
   **2026-11-03 利用者の判断：採る**（戦略 v2 §9-1。M3 で flow memo の後に、shadow mode を gate にして 1 つずつ）。
2. **lazy member table**（R2、memory −23%）：tsgo の pin（`aa8149273`）にはなく、depth 制限付近で診断が変わりうる → 採らない
   （2026-11-02 の判断）。
3. **leaf file の解放**（R5、VS Code memory −13〜−16%）：file の生存期間の設計（CLI の `--noEmit` 限定、LSP では不可）。
   **2026-11-03 利用者の判断：採る**（CLI の `--noEmit` 限定、M5）。
4. **flow memo**（R17、exact、VS Code −2.2%）：採るなら shadow mode で exactness を確認してから。
   戦略 v2 では M3 の最初（C-0）に置いた（shadow mode を gate に）。
5. **`unsafe` の範囲**：node の tail を header の後ろに置く tsrs の形は cast が要る。§6.2 の形（固定 32 B + tail word store）は
   `crates/store` の外は safe。名前表の平坦化（§6.1-3）は `from_utf8_unchecked` と固定 address の text arena を `crates/store` に
   置く（規則の範囲内）。1% 以下の差なら safe を選ぶ。
6. **known name の seed で全 `EscapedName` の id がずれる**（§6.1-4）：id は出力に出ないが、`EscapedName` を key にする hash 容器
   23 個のどれかを走査していれば順序が変わりうる。8 case の byte 一致 + conformance で gate する前提で進めてよいか。
   **2026-11-03 利用者の判断：後回し**（利用者が戻すまで入れない）。
7. **string literal の text を process 全体の名前表に intern する**（§6.1-2、−50 MiB）：LSP では edit ごとに表が育つ（今の
   append-only の根拠は識別子の語彙が有界なこと）。CLI だけ採る／program ごとの arena にする／上限で切る、のどれか。
   **2026-11-03 利用者の判断：後回し**（6 と同じ）。
8. **relocate の廃止で loader が parse した tree の id が program 順でなくなる**（§6.2）：出力には出ないが、file をまたぐ生の
   NodeId の比較が残っていれば順序が変わる。監査してから採るか、discovery 順で決定的に lease する形にするか。
   監査の結果（2026-11-03、`target/claude-tools/handover/perf-tsrs/node-order-audit-report.md`）：file をまたぐ node id の順序に
   依存する出力は見つからない。M1 では relocate を 32 B record の複製として残し、program 順が分かるところだけその場に作る案。
9. **slice の順序**（§6.0）：「効果の大きい順」なら複製と確保（12）→ 文字列（13）、2026-11-02 の合意なら文字列が先。

## 9. 落とし穴と教訓

- `StoreVec` は Vec 形（ptr, len, cap）でないと遅い。`StoreVec::record` は debug でだけ bound を見る。
- parse の buffer は mimalloc に残る（+380 MB VS Code）：≥ 64 KiB は mmap、bind の symbol は予約 slot にその場で作る。
- `CheckResult<T>` = `Result<T, CheckAbort>`（uninhabited）は費用 0。`perf::bump` は `perf-counters` feature なしでは no-op。
- `cargo check --message-format=json` の span で機械的な書き換え（`Box::new`/deref、`.clone()` の削除）をする。
- 同じ base から作った binary 同士を比べる。PGO 同士、通常同士。wall time は noise。
- PGO：CLI の `_exit` が profile を書かない（§3.2）。
- 並列 test で active な range を数える test は flaky → `IdentityLease::watch`。
- `#[inline]` の入口 + `#[inline(never)]` の本体（R19）は効く（slice 10）。多数の呼び出し元を持つ関数の本体 inline は負ける
  （tsrs 2a）。
- tsgo の形を先に確認する（例：object literal の regular type は side map。§2.2）。tsgo の Go 源は
  `target/typescript7/upstream/tsc/internal/checker/*.go`。
- scratchpad（`/private/tmp/claude-501/...`）は 3 日で消える。残すものは `target/claude-tools/handover/perf-tsrs/` へ。
