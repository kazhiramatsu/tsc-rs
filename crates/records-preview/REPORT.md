# Phase 0.3 record layout report

Generated by `python3 crates/records-preview/tools/memory_report.py`. Inputs are bundled under `inputs/`; original local paths and SHA-256 are in `inputs/provenance.json`. This is layout arithmetic, not a performance result.

## Accounting rules and limitations

- Node header = 24 B; tail = `8 * ceil(words / 2)` B. The preview reserves header w5 and starts its typed tail at byte 24. This follows the SPEC formula; overlapping payload with w5 would be a different ABI and arithmetic.
- Type header = 24 B including dense per-checker `id`; w5 is the payload tag. Payload and inline links follow at byte 24, padded to 8 B. Mapped and Conditional spill only named cold fields when fully inline size exceeds 64 B; hot members remain inline.
- Plain records accept all bit patterns. Nullable `Id<T>` is raw u32, `OptionalSpan<T>` stores start/len+1, and booleans/enums are integer codecs. These avoid the invalid-zero `Ref`/`Span` and Rust-enum problems in a literal transcription of SPEC-arena.
- B-3 was measured on an older source revision; population counts are used as a workload model, not as current binary layout measurements. The fixed Type comparator is the SPEC's 40 + 24 = 64 B.
- **The supplied B-3 streams contain no TypeData-kind population rows.** Every per-kind population and weighted Type byte total below is therefore unmeasured. Use `--type-populations path.json` to fill this gap; the script verifies the aggregate against the memory row.
- `data()` builds owned decoded Data values; hot access is `KindRecord::tail()` / `TypeKindRecord::tail()`. The integrator must price owned decoding through SPEC-0b ceiling (iv). The safe stub does not demonstrate native address projection or its cost.
